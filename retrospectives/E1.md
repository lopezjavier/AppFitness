# E1 retrospective · Infrastructure and app skeleton

2026-10-12 → 2026-10-13 · `v0.1.0` · held 2026-10-13

## User feedback

- Setting a model per agent improved token usage a lot.
- Two epics done, one per day. Performance is the main priority: it is good, but more speed was expected.
- Concern that performance will drop as epics add complexity.
- Memory keeps growing and performance seems to drop after `/compact`. Keep `CLAUDE.md` small so nothing important is missed; rules go in their own section.
- The user compacts after about 2 tasks. They like the checkpoints and expect more autonomy between them, with compaction kept in their hands: the PM runs until stopped. Automatic compaction is a no-go, because performance and token usage are better with a small context.
- QA's value was questioned: it spotted no app bug in E1. The user proposed running QA per task in parallel, without blocking the next task, with findings as GitHub issues fixed between tasks, and waiting for all QA only at checkpoints.
- Product feedback at a checkpoint is the expected interaction, not a process failure. The user acts as product owner and may challenge mockup decisions, such as the "+ Registro" button, when the experience feels awkward.
- Checkpoint decisions must not be postponed: Checkpoint E1-A was forgotten.
- Keep a retrospective per epic in its own folder, and repeat it after every epic.

## PM view (lessons that carry over to other projects)

- **Turn every repeated review finding into a script.** Prose rules drifted across sessions; the mistakes stopped for good only once a check enforced them (hardcoded dp → tokens guard; encoding → `check-text-encoding.sh`; untagged flows → `check-e2e-tags.sh`).
- **Independent review earns its cost; per-task end-to-end tests did not.** The strongest model on review caught 7 real defects. Emulator runs caught none, were the slowest step and the main source of flakiness. Host UI tests give most of that coverage in seconds.
- **Each agent hand-off has a fixed cost**, because every agent starts cold and re-reads its context. With 6–7 hand-offs per task, small tasks spend more on the pipeline than on the work. Size tasks as vertical slices of a story, not single components.
- **Keep shared state in files, not in the conversation.** The plan, task list and log survived every compaction; what lived only in chat was lost or had to be repeated.
- **Mechanical steps are safer as deterministic commands than as an agent.** Packaging commits is mechanical, yet it caused the worst slip of the epic (a re-encoded test file).
- **Write the environment's constraints down early.** Windows encoding and line endings, page-file limits for parallel Gradle and emulator quirks each cost a debugging round before they became rules.
- **Upfront planning paid off.** Gherkin stories and ADRs meant almost no product questions mid-task. The questions that did arise came at checkpoints, where they belong.

## Agreed changes

- QA runs in the background after each merge and reports app bugs as `qa` GitHub issues; checkpoints wait for all QA and a green full regression (ADR-23).
- The PM chains tasks up to each checkpoint and only stops when the user asks; subagent replies capped at 10 lines to keep the context small.
- Durable rules moved from the PM's memory into a "Working rules" section of `CLAUDE.md`.
- Every open 👤 item is presented at its checkpoint; Checkpoint E1-A marked approved.
- Text files must be UTF-8 with LF, with a CI guard, after an encoding slip garbled a test in PR #35.
- Tasks are sized as vertical slices of a user story (the epic breakdown is done by a dedicated agent with project sizing rules), to cut the fixed hand-off cost per task. Tried in E2 and compared at its retrospective.
- 👤 checkpoints only where the user can try a meaningfully new journey on the phone (1–3 per epic, closure included): the balance between autonomy and user feedback is the key to this workflow.
- A finding that pr-reviewer reports twice becomes a script or CI check within the epic.
- The log records each task's duration, so the next retrospective has numbers.
- pr-creator makes one commit per task (PRs are squash-merged) and never re-encodes files; it stays an agent now that a CI check covers the encoding slip.
- The "+ Registro" button is decided per epic (E3–E5), and the tablet's primary action leaves the NavigationRail in a later epic (`tasks/todo.md`, "Notes for later epics").
