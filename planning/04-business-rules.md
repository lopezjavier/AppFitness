# Business rules and formulas (current)

Implemented as pure functions in `shared/domain/usecase/` with unit tests that include the examples below. Full prose, extra examples and history: [`phase1/04-business-rules.md`](phase1/04-business-rules.md). Section numbers are cited by code; do not renumber.

## 1. Energy and macros

### 1.1 Constants
Protein 4 kcal/g, carbohydrates 4 kcal/g, fat 9 kcal/g.

### 1.2 BMR (Mifflin-St Jeor)
Male `10·kg + 6.25·cm − 5·age + 5`; female `… − 161`. Age in full years from `birth_date`; weight = latest `body_measurements` row.

### 1.3 TDEE
`TDEE = round(BMR × factor)`: sedentary 1.2 (Sedentario), light 1.375 (Ligero), moderate 1.55 (Moderado), high 1.725 (Alto), very_high 1.9 (Muy alto). Each level is a selectable card with title + description. Example: male, 26, 178 cm, 74.2 kg, moderate: BMR 1729.5, TDEE **2681**.

### 1.4 Calorie target
- `target_kcal = TDEE + calorie_adjustment`. Default adjustment: Deficit −400, Maintenance 0, Surplus +250. Steps of 50 within Deficit [−1000, −50], Maintenance [−100, +100], Surplus [+50, +750].
- Safety floor by sex (ADR-25): 1200 kcal women, 1500 kcal men; below it the target is the floor and a warning shows.
- Label by |adjustment|: <= 300 ligero, <= 600 moderado, > 600 agresivo (e.g. "−400 kcal · Déficit moderado").
- Recalculated only when the user saves in Preferencias (ADR-24), with the latest weight; stored in `nutrition_goals`. Logging weight does not change it.
- No goal progress: the target weight is no longer a user input (ADR-78, T-162); "Peso" shows the accepted plan's weight outcome (§8) read-only, with no distance and no progress bar.

### 1.5 Macro split (auto-balance)
Integer percentages each in [5, 90], summing to 100; default P 30 / C 45 / F 25. Moving a slider by Δ distributes −Δ over the other two proportionally to their current value, largest-remainder rounding; if one hits 5 the rest goes to the other; if both are 5 the slider cannot rise. Grams = `round(target_kcal × pct / 100 / kcal_per_gram)`. Example (2400 kcal): 30/45/25 -> 180/270/67 g; P to 35 -> C 42, F 23 -> 210/252/61 g.

## 2. Diary
- Base unit `g` (solids) or `ml` (drinks); nutrition per 100 base units. Entry `kcal = kcal_100 × amount / 100` (same for macros), amount to 0.1, stored as a snapshot; editing a manual food applies to future entries only (ADR-53).
- Nutrients are listed in Spanish label order (EU 1169/2011 Annex XV, then vitamins/minerals); absent values hidden.
- A named portion resolves to an amount in base units; the entry stores the amount and a `portion_label` snapshot.
- Meal/day totals = sum of snapshots; UI shows kcal and base unit without decimals. `remaining = target − consumed`; negative shows "+N kcal en exceso" with the over-target ring.
- Macro progress `round(consumed_g / target_g × 100)` %; bar capped at 100, text shows the real value.
- Example (target 2400; 180/270/67 g): consumed 142/210/48 g = 1840 kcal -> "1.840 / 2.400 kcal", P 79 %, C 78 %, F 72 %.

### 2.1 Diary history (US-24)
Per-day summary = day totals. Weekly average = mean of day totals over logged days in the last 7 days. Monthly total = sum in the calendar month; its average uses logged days only.

### 2.2 Cooking methods (US-50, ADR-65)
Only `g` foods; default Crudo. Added fat = `round(raw_g × pct / 100, 1)` g and `round(9 × fat, 1)` kcal; protein, carbs and micronutrients unchanged. Defaults (Preferencias -> Cocina, 0-20 %): A la plancha 1 %, Air fryer 2 %, Frito 8 %. The entry stores adjusted `kcal`/`fat_g`, `cooking_method`, `cooking_oil_retained_g`; per-100 values never change. Saved comidas store a method per item and recompute the fat from current preferences when added. A change applies to future entries only. Example: 200 g chicken (110 kcal, 3 g fat /100 g) fried = 364 kcal, 22 g fat.

### 2.3 Default comidas (US-51, ADR-61)
- A default is a saved comida per meal and ISO weekday (Mon = 1); its meal slot is authoritative. Days assigned to another comida for that meal are not selectable.
- Evaluated for today only, on the first Diary load: if `diary_default_applications` has the day, nothing; if the day already has entries, mark it and add nothing; otherwise copy the comidas as normal entries (current amounts, saved methods, current cooking preferences) and mark the day. No backfill, no re-add after deletion. The server rejects dates more than one day from UTC today (`22023`).
- Deleting a meal or comida cascades its assignments; logged entries are unchanged. A failed apply never blocks the Diary (non-blocking retry, idempotent).

## 3. Weight
- **3.1 Daily value:** several measurements on one local day -> their average.
- **3.2 MA7:** average of available daily values in `[d − 6, d]`; one day suffices (ADR-49); the chart connects consecutive points across gaps.
- **3.3 Weekly rate:** `(w_last − w_prev) / days_between × 7` kg/week, 2 decimals, over the last two days with data; fewer than 2 -> "Sin datos suficientes". Colour: Deficit rate < 0 green else red; Surplus rate > 0 green else red; Maintenance |rate| <= 0.20 green else amber.
- **3.4 Chart filters:** 1S 7 d, 1M 30, 3M 90 (default), 6M 180, 1A 365, back from today; the first day's MA7 uses data before the range when available.
- **3.5 Plan outcome (ADR-78, T-162):** there is no user-entered target weight (the `profiles.target_weight_kg` column is dropped). "Peso" shows the accepted plan's weight outcome as a read-only "Objetivo del plan" card (value, deadline, reason behind `?`) only when the plan has one, and the chart's dashed line sits at that value. No distance, no progress bar, no ETA.
- **3.6 BMI:** `kg / (cm/100)²`, 1 decimal, derived, hidden without height.
- **3.7 Health Connect:** weight -> `weight_kg`, body fat -> `body_fat_pct`, lean mass, body water, bone, BMR -> their columns. Read: weight and body fat within ± 2 min form one measurement; composition merges by instant; `external_id` prevents duplicates; records written by this app are skipped. Write (permission granted): manual weight/body fat/composition are written back, the record id is stored, edits update and deletes remove the copy; a failed HC call never blocks the app. Imported readings deleted in the app stay deleted. Sync is on demand ("Sincronizar") plus the daily automatic sync on the first open of a day (§3.12); never in the background. A Health Connect weight wins for its day (ADR-47).
- **3.8 Interpretation (informative, with the non-medical disclaimer "Este producto no es un dispositivo médico; los resultados no sirven para diagnóstico"):** BMI < 18,5 underweight, 18,5-24,9 normal, 25,0-29,9 overweight, >= 30 obese. Body fat men < 10 low, 10-20 normal, 20-25 high, > 25 very high; women < 18, 18-28, 28-32, > 32. Shared edges belong to the lower band; BMI compares the rounded value. WHR men <= 0,90 low risk else high; women <= 0,85.
- **3.9 WHR:** latest waist / latest hip, 2 decimals; both required, else "Sin datos suficientes".
- **3.10 Watch data (E11, [epic](epics/E11-health-connect-daily-sync.md)):** `daily_activity` holds one row per user and day (day = device time zone), whole-replaced on every re-sync (a re-read day is complete, nulls included). A sleep session belongs to the day it ends on and is identified by its `external_id`; a session edited in the watch app replaces the stored one. One resting heart rate per day, the latest kept. `health_sync_state.last_auto_sync_date` is written only after a successful automatic sync, through `mark_health_auto_sync`; the import never changes it.
- **3.11 Watch sync and display (T-141, US-61..US-63):** one "Sincronizar" runs the weight sync and the watch import, each only if its permissions are granted and each failing on its own (the call fails only when every part that ran failed). Window: 90 days when `last_auto_sync_date` is null (so every manual sync until the automatic sync ships), otherwise the last 7 days, re-read whole by local day; no Changes token for these types (daily granularity). Before sending, values are clamped or dropped to the DB ranges: steps 0..1 000 000, kcal 0..100 000 (2 decimals), sleep minutes 1..1440, resting bpm 20..250 (outside is dropped, never clamped), `external_id` <= 200, at most 400 rows per array (newest kept); a daily row with no value is dropped. Sleep minutes = time in light, deep, REM and sleeping stages (the whole session when it has no stages). Write permissions are only weight and body fat; the history permission is requested with the reads. "Actividad" (Perfil > Estadísticas) shows, per value, the most recent of the last 7 stored days that has one (sleep: the latest session, dated by the local day it ended), as read-only cards; a value with none has no card, and with none at all the screen offers "Ir a Peso".
- **3.12 Daily automatic sync (T-142, US-60, ADR-74):** on the first open of each local day (cold start, or return to the foreground on a new local day) the app runs the §3.11 sync for every granted type. Due = `last_auto_sync_date` is null or strictly before today's local date; it also needs Health Connect available, connectivity and at least one read permission. It never opens the permission dialog (missing permission is shown passively as "Permiso necesario"). Only a fully successful sync stores `last_auto_sync_date` (a failed `markAutoSynced` just retries next open); a failure, offline or a partial failure leaves it, so the next open retries. A tap on "Sincronizar" while an automatic sync runs joins it (one read); after it finished, a tap reads again. The first-window watch read (90 days) falls back once to 30 days if it throws; the 7-day window has no fallback. When exactly one part (weight or watch data) fails the other still imports and the outcome names the failed part (`SyncPart`). A sync that imported a weight refreshes the reminders.

## 4. Training
- **4.1 Estimated 1RM (Epley):** `w × (1 + reps/30)` for 2-12 reps; reps = 1 -> `w`; reps 0, > 12 or weight 0 do not count; round to 0.5 kg; session 1RM = max over completed sets. 100 × 5 -> **116.5**; 85 × 8 -> **107.5**.
- **4.2 Volume:** `Σ weight × reps` over completed sets (`completed_at` not null); bodyweight/assisted/weighted per §4.7; duration/distance exercises 0. Weekly muscle volume: ISO week (Mon-Sun) by `muscle_group`.
- **4.3 Ghost data:** per exercise, the sets of the most recent completed session containing it, matched by `set_index` ("—" if fewer), format "85 kg × 8", shown as dim placeholder in KG/REPS. A pending set from a planned routine set shows the planned weight/reps instead (ADR-50); the live row has no ANTERIOR column (T-153: the note button took its width; the previous performance is only the dim placeholder, no tap-to-fill).
- **4.4 Rest timer:** the exercise's `rest_seconds` (default 120; 0 = none); starts when a set completes (restarts on another); "+30s", "Omitir"; computed from an end instant so background is safe; at 0 vibration + the alarm sound unless muted; in a superset it starts after the group's last exercise. **Alert outside the app (ADR-75, US-64):** while a rest runs, an exact alarm is scheduled for its end instant; with the app in the background, the screen off or the process killed, it posts the "Descanso terminado" notification, whose channel vibrates (three pulses) and plays the chime ("Campana suave", the only sound, `rest_chime`, channel `rest_alert_chime`); in the foreground (a resumed activity) only the in-app alert fires and the alarm is cancelled. "+30s" and a new set reschedule it; "Omitir", finishing and discarding cancel it; pausing the session keeps it. A notification more than 10 minutes late is dropped. If notifications are denied nothing is posted and the app explains it once; the rest is never blocked. A reboot clears the alarm (accepted: a rest lasts 10 minutes at most).
- **4.5 PR in summary:** an exercise is a PR when its session 1RM exceeds all previous sessions.
- **4.6 Set types:** `working`, `warm_up`, `failure`, `drop`. Volume, 1RM, PRs and totals ignore `warm_up` unless "Incluir calentamiento" is on (toggling recalculates past and future). Types can be set while planning and logging.
- **4.7 Volume options:** per-hand exercises (`exercises.per_hand`, ADR-56): `volume = 2 × weight × reps`, 1RM unchanged. `bodyweight`/`assisted`: `(latest body weight ± added/assisted) × reps`; `weighted` counts the added load only.
- **4.8 PR catalogue:** per exercise family `best_1rm`, `heaviest_lift`, `best_set` (single-set volume), `max_volume` (session), `total_reps` (all-time, ADR-52), and for duration/distance `best_duration`, `best_distance`, `most_steps`, `most_floors`. Shown in the session summary, exercise detail and workout detail; respects §4.6. The live PR notification is deferred (ADR-52).
- **4.9 Calculators (ADR-52/55/56):** warm-up from working weight W: bar × 10, 40 % × 5, 60 % × 3, 80 % × 2, rounded to the derived rounding and never below the bar; 1-4 sets chosen per use (default 1 = 60 % × 3; 3 -> 40/60/80; 2 -> 50/80 × 5,2; the bar set only with 4). Bars 20, 15, 10 (EZ), 7,5 kg (default 20). Plates per side 25, 20, 15, 10, 5, 2,5, 2, 1,25, 1, 0,5 (all on by default). Disc loader: 0-10 discs per weight per side, total = bar + 2 × side sum, read-only (20 kg bar + 25 + 15 per side = 100 kg). Rounding is derived: 2 × smallest enabled plate. Dumbbells: handle (default 1 kg, 0,5-10 in 0,5 steps) acts as the bar, per dumbbell.
- **4.10 Duration and pauses (US-38):** `duration = end − started_at − paused_total_s`, never below 0 (`end` = `ended_at`, else `paused_at` while paused, else now). Resuming adds whole seconds since `paused_at` (negative adds 0). Pausing does not affect rest or set stopwatches; "Finalizar entreno" needs at least one completed set. "Última vez en esta rutina" mode considers only sessions of that routine.
- **4.11 Statistics (US-40/41):** eligible = `completed` sessions with UTC `started_at` date in `[p_from, p_to]` (null = open), completed sets, warm-ups only when included. `workouts` counts sessions once (even with no eligible set); `volume = Σ set_volume × factor`; `duration` = Σ per session of `greatest(0, ended_at − started_at − paused_total_s)`. Weeks start UTC Monday. Sets per muscle group: primary +1, each distinct secondary +0.5 (secondary equal to primary adds nothing); ties in `muscle_group` enum order; `full_body` is handled by the client. `exercise_set_counts` with a group weighs 1/0.5 and excludes exercises without it. Example: bench (chest; triceps, shoulders), 3 working + 1 warm-up: chest 3, triceps 1,5, shoulders 1,5 (with warm-ups 4/2/2).
- **4.12 Exercise discomfort (T-147, US-67):** the user flags an exercise ("Registrar molestia") with an optional note (trimmed, empty = none, <= 200 chars, else `Validation`); online only. A discomfort is **open** while `resolved_at` is null and `now < logged_at + 7 days` (exactly 7 days = expired; `now` comes from the injected `Clock`); an open one shows, in one block on the exercise (in this and later sessions), the level dot, the level text and "Ya no me molesta" (no "Molestia registrada" label). Logging again while one is open adds a row and the newest open one is shown. "Ya no me molesta" sets `resolved_at = now` on every unresolved row of that exercise; rows are never deleted (history for E13). **Level (T-152, ADR-81):** logging requires a level 1-5, chosen by the user with no preselection: 1 Tensión o fatiga, 2 Molestia leve, 3 Pinchazo o chasquido, 4 Hinchazón, hormigueo o entumecimiento, 5 Dolor agudo o lesión; stored in `level` and immutable. **Severe = level >= 4**, derived in the domain (the `severe` column was dropped). The note is never interpreted: no term matching and no health message. Rows that existed before T-152 were mapped by the migration: severe true -> 5, severe false -> 2 (level 1 is only for new rows). The highest level among open rows is the one shown. **Amended 2026-11-01 (ADR-89, `07` §7; detail in T-194):** "no health message" becomes "no generic message": one note, once per discomfort, when a level 4-5 discomfort is still **unresolved** 14 days after it was logged or was logged at level 4-5 on the same exercise in 3 sessions (dismissible, never blocking, from levels and dates only). **Unresolved** (separate from open, `07` §7): a level 4-5 row with `resolved_at` null, whatever its age, until "Ya no me molesta" or step 3 of the graded return; it stays shown on the exercise with "Ya no me molesta" after the 7-day open window, and it is what the summary and the block review read for level 4-5. The 7-day open window keeps governing the level 1-3 load block. A level 4-5 exercise (or one loading the intake's injured area) leaves the next block and follows the 3-step graded return of `07` §7, paced by the user.
- **4.13 Training intention and preferences (T-149, US-65):** intention (Ganar fuerza, Ganar musculatura, Perder grasa, Recomposición, Mantenimiento), place (Casa, Gimnasio, Otro), equipment, days per week (1-7) and session length (15-180 min, 5-min steps) are all optional and clearable. Choosing a place replaces the equipment with its default (Casa = mancuernas, banda, peso corporal; Gimnasio = all; Otro = peso corporal), which the user can then edit. The intention never changes the nutrition goal (calorie target stays with E13). The section saves only its own five columns.
- **4.14 Progression suggestion (T-159, US-70):** double progression per exercise, deterministic, computed in SQL by `progression_suggestions(p_session_id)` from the user's own sets (no model, no usage limit). Needs a rep range (`rep_min`-`rep_max`) on the routine exercise; each set of a session carries the range snapshot it was started with, and only earlier **completed** sessions with the exact same (min, max) count; the "last two" are the two most recent of those by `started_at`. Only `working` completed sets count (warm-ups, `failure`, `drop` excluded). Latest matching session S1: all sets with reps >= `rep_max` and highest RPE <= 8 (sets without RPE are judged on reps only) -> `raise_weight` (base = S1 top weight, goal = `rep_min`); else if more than half the sets are below `rep_min` in both S1 and the previous session -> `lower_weight` (base = S1 top weight); else `add_rep` (same weight, goal = best S1 reps + 1, capped at `rep_max`). No matching session -> no suggestion. Open discomfort (§4.12) of level 1-3 turns a raise into `add_rep` with reason `kept_discomfort` (goal = `rep_max`); level >= 4 gives no suggestion; no health text (ADR-81). The client applies the weight change: raise adds the step, lower subtracts 5 % of the base, both rounded to the step; step = 2 x smallest enabled plate (§4.9), dumbbells use the handle step, machines/other the same plate step. Examples: 80 x 6,6,7 on 6-8 -> 80 kg x 8; 8,8,8 at RPE <= 8 with a 2,5 kg plate -> 85 kg x 6; lower 80 -> 76 -> 75. The suggestion never writes sets or the routine. **Inside an accepted block (T-227, ADR-88, `07` §3):** the raise and the 5 % drop **apply on their own**; the paragraph above holds only outside a block. **Trigger:** the client calls `apply_coach_progression(session_id)` once the "update the routine?" question (ADR-70) is resolved (auto-update done, sheet answered or dismissed, or nothing to ask), so the coach's write always goes on top of `update_routine_from_session`; the reverse order is not supported. It acts only on a completed session whose routine is in the folder of the user's `accepted` plan, and per exercise only if that session is the latest completed one with that range (a late retry never overrides newer data). Idempotent: a second call returns the rows of the first and writes nothing. **Decision and step** are computed on the server by the same core as `progression_suggestions` (`progression_decision_core`, S1 = the finished session), the step from `training_preferences` (`coach_load_step`): dumbbells the handle weight, everything else 2 x the smallest enabled plate (§4.9). Raise = base + step; drop = base x 0.95 rounded to the step (80 -> 76 -> 75), always at least one step lower. **Write:** for every routine of the plan's folder holding the exercise with the same `(rep_min, rep_max)`, the planned **working** sets with a weight get the new weight (absolute; warm-up, drop and failure sets and sets without weight are untouched); a raise also sets their planned reps and the routine-exercise summary to `rep_min`. Every applied change is a `coach_changes` row (`load_raise`, `load_drop`) with before/after snapshots keyed by routine and exercise. **Over 10 %:** when `step / base` is strictly more than 10 % (6 kg dumbbells + 2 kg handle = +33 %; exactly 10 % still raises) nothing is written and a `load_flag` row (`pending`, `step_over_10_percent`, figures `current_kg`, `step_kg`, `next_kg`, `percent`) waits for the user; while it is pending later sessions of that exercise write no weight and no second flag. `decide_progression_flag(id, 'raise')` applies the stored step as a new undoable `load_raise` row (`origin_flag_id`); if the planned weight changed since the flag it raises `coach_change_conflict` and the flag stays pending. `'keep'` adds 2 to `rep_max` (cap 50) in every block routine holding the exercise with the flag's range, keeps the weight and is not undoable. An exercise done without a rep range gets a `no_range_flag` (`no_rep_range`, nothing written, no decision); it closes by itself (`decided`, `range_added`) the next time the RPC runs after the exercise has a range. **Discomfort:** an open level 1-3 on a due raise writes no weight and one `load_kept` row (`kept_discomfort`, not undoable); level 4-5 writes nothing. **Undo** (`undo_coach_change`): per routine, restores the snapshot only where the current planned values still equal what the coach wrote; a routine the user (or the coach) changed since is skipped, the user's edit wins. At least one restored -> `undone` and `{restored, skipped}`; none -> `coach_change_conflict`; a row that is not an applied raise/drop, or already undone -> `coach_change_not_undoable`. **Deload weeks:** a session done in a week of the plan with an accepted deload (`coach_plan_sessions.deload`) gives no change, never raises, and is skipped (not a reset) when counting the two failed sessions (`07` §3). **After 14 or more days** without a completed session of the exercise, the first session keeps the last load (no raise) and one failed session (instead of two) triggers the drop (`one_session_below_min_after_gap`). The coach's write depends on the client calling the RPC after the finish flow; a session whose call never happens (app killed) is not caught up later.
- **4.15 Deleting a routine folder (T-211, US-35, ADR-95; supersedes ADR-51):** a folder with at least one visible (non-archived) routine cannot be deleted: "Borrar carpeta" in the folder's ⋮ menu (dimmed, still tappable; the trash icon left the row, T-214) answers with the message «Mueve o elimina las rutinas de la carpeta para poder eliminarla.» (no dialog) and nothing changes. The user first deletes its routines or moves them out with "Mover a carpeta". An empty folder is deleted at once. Archived routines (not listed anywhere) do not block and are deleted with the folder. The server enforces it. A block folder (ADR-94) follows the same rule; "Eliminar bloque" keeps the folder and its routines. Past workouts keep their data (`routine_id` set null) when their routines are deleted.

## 5. Formatting (UI, Spanish)
Thousands "." (also 4 digits, "1.840") and decimal ","; custom formatter in `commonMain` (CLDR `es-ES` does not group 4 digits). Weight, cm and BMI 1 decimal; WHR 2; kcal and grams none; integer percentages. Dates: "Hoy", "Ayer", "lun, 24 oct".

## 6. Reminders and weekly check-in (E10, ADR-73)
- **6.1 Reminders:** computed on the client at each open or return to the foreground, never stored, no system notifications, no time window: a condition met while the app was closed is listed on the next open ("Centro de avisos").
- **6.2 Weight:** listed when the latest weigh-in is 2 or more days old (2 days in a row without one). **Circumferences:** listed when the latest circumference is 14 or more days old. A Health Connect weight stored for today clears the weight reminder.
- **6.3 Silencing:** each type (weight, circumference, check-in) is silenced in Preferencias > Avisos through `notification_settings`; a missing row means enabled; a silenced type is neither listed nor counted.
- **6.4 Check-in day:** `profiles.check_in_weekday` (1-7, default Sunday). From that weekday the current week's check-in (week = ISO Monday-Sunday) is listed and counted; unanswered, it stays listed until the next check-in day, when only the current one is listed (never two); not listed before the first check-in day.
- **6.5 Answer:** energy 1-5 (required) and optional notes (<= 1000 chars), one row per user and week; saving removes the reminder. An answered check-in can be edited (same row, `updated_at` refreshed). Sleep is not asked.
- **6.6 Summary (deterministic):** this week's training volume against last week's (`weekly_set_counts`), the week's records (`weekly_records`) and the week's weight trend.
- **6.7 Weekly summary notice (T-231, US-98):** one "Centro de avisos" item while the latest finished plan week of the accepted block has a summary (`coach_week_summary`, §9) that the user has not opened. It is listed (and counted) while unseen and silenced by the notification kind `week_summary` (Preferencias > Avisos, default on, a missing row means enabled). Opening the summary calls `mark_coach_week_summary_seen(plan, week)`, which stores `(user, plan, week)` in `coach_week_summary_seen`, so the item clears on every device; the next finished week adds one new item. An empty or paused week has no summary and no item (no fallback to older weeks). Sets per group use primary 1 and secondary 0.5 on exercises that count for H1 (`07` §3), so they can differ from the statistics (§4.11).
- **6.8 "¿Por qué no progreso?" (T-232, US-105):** a main lift is stalled when its weekly best e1RM did not improve over the last 3 plan weeks done (`max(w2, w3) > w1`, ties stall; deload weeks and weeks without a workout are skipped; fewer than 3 weeks: no stall). `coach_stall_diagnosis` gives the first cause that fires, in order: workouts per week under 2; sets per week of the lift's group under 10 (skipped for "Ganar fuerza"; "Mantener" variant when the plan gives the group under 10); protein under 1,6 g/kg with at least 10 complete diary days; sleep under 7 h with at least 10 nights; else no clear cause (flagging missing food records when the protein check lacked days). The weekly summary shows a stall only in the week it is first found (not stalled one plan week earlier). Text and thresholds: `07` §3 (7).

## 7. Coach derived values (E13, T-157, [coach design](07-coach-design.md) §2)
SQL: `coach_derived_estimates`, `confirm_derived_values`, `coach_summary`. `p_today` is the client's local date (`22023` beyond one day from UTC today, as §2.3); windows end at `p_today`; days are UTC dates on the server. Nothing here writes `profiles` (the Diary keeps using `profiles.activity_level`).
- **7.1 Activity level.** Window: the last 28 days. A source needs 7 days with data, else it is *missing*. Steps (average of days with steps, bands of Tudor-Locke et al. 2011): under 5 000 sedentary, 5 000-7 499 light, 7 500-9 999 moderate, 10 000-12 499 high, 12 500 or more very_high. Without steps, average active kcal per day (device-dependent, low confidence): under 150 sedentary, 150-299 light, 300-499 moderate, 500-749 high, 750 or more very_high. Active kcal is listed as a source whenever present. With neither, the level is `profiles.activity_level` (sedentary when null), source `profile`. Completed sessions per week (started in the window): 3 or more raise a measured level by one (cap very_high); sessions never change the profile level (it already includes training). Estimate = factor of §1.3; uncertainty (half-width) 0.1 with data, 0.2 profile-only. Missing codes: `steps`, `active_kcal`, `training_history` (no completed session in the window).
- **7.2 Effective level and expenditure.** Effective level = the confirmed (possibly edited) level when the key is confirmed and not re-asked, else the estimate. Basal: §1.2 with the latest weight, null with missing sex, birth date, height or weight (`profile_data`). Total expenditure: `adaptive` whenever the intake is reliable (§7.3): `round(anchor_kcal − slope term)`, where the slope term `slope_kg_week × 7 700 / 7` is used (`slope_used = true`) only if **all** hold: the weight trend has 4 or more weekly averages (not `low_confidence`), at least 8 distinct weigh-in days in the 8-week window (`weigh_in_days`, §7.4) and the intake is reliable; otherwise `slope_used = false` and the expenditure is `round(anchor_kcal)` (weight assumed stable). Unreliable diary: `round(BMR × factor)` (`source: formula`, no anchor). The `coach` function additionally clamps the slope term to ±0.5 % × weight × 11 kcal (one top-of-range rate, §8.7), so a noisy slope cannot move the expenditure further (T-180, ADR-84, *design decision*). Uncertainty 10 % of the value.
- **7.3 Intake.** Logged days = days of the 28-day window with at least one diary entry; reliable when `logged_days × 10 >= 196` (70 % of 28 is 19.6, so 20 days; 19 days is not). Unlogged days are excluded from the mean, never zero. **Anchor (T-180, *design decision*):** with a reliable diary, `m` = median of the daily sums; days under 40 % of `m` are partial logging and are excluded (not zeroed); days over 150 % of `m` are capped at 150 % of `m`; `anchor_kcal = round(mean of the remaining days)` (e.g. a 4 446 kcal day against a median of about 2 200 counts as 3 300; a 600 kcal day drops out). `mean_kcal` stays the raw mean; ~~`logged_days` and `reliable` count raw logged days~~ **amended 2026-11-01 (`07` §2, one partial-day rule):** `logged_days`, `reliable` and the weekly gate of §8.5 count only complete days (partial days under 40 % of `m` are excluded from the counts too). No anchor (null) without a reliable diary. Unreliable: `unreliable = true`, `allow_calorie_changes = false`, expenditure falls back to the formula.
- **7.4 Weight trend.** Daily value = average of the day's measurements (§3.1); weekly average per ISO week (Mon-Sun) over the 8 weeks ending the week of `p_today`; slope = least-squares slope of the weekly averages against the week index, kg per week (3 decimals). Interval = slope ± t × s / √Sxx with t(95 %) for df = weeks − 2 (12.706, 4.303, 3.182, 2.776, 2.571, 2.447). 2 weeks: slope, no interval; fewer than 4 weeks: `low_confidence`; fewer than 2 weeks: no slope, missing `weigh_ins`. `weigh_in_days` = distinct days with a measurement in the same 8-week window. Never blocks. Re-ask uncertainty = interval half-width, 0.5 kg/week without an interval. Example: weekly 80, 79, 79, 78 -> slope −0.6, interval [−1.209, 0.009].
- **7.5 Experience.** Beginner under 24 completed sessions or under 12 weeks of history (weeks between the first completed session and `p_today`, also with no history); advanced from 150 sessions and 52 weeks; intermediate otherwise. Ordinal 0-2, uncertainty 0.5. **Amended 2026-11-01 (ADR-86, `07` §2; detail in T-185):** experience = the higher of this history class and the self-reported class of the intake (consistent lifting under 6 months beginner, 6 months to under 2 years intermediate, 2 years or more advanced), shown as "según lo que nos contaste" while the self-report wins; a returning lifter keeps the class. "Without history: beginner" holds only without an intake. The intake's known maintenance replaces BMR × factor as the expenditure prior until the adaptive expenditure qualifies (§7.2-§7.3). **Rules as built (T-185):** self-reported class from `training_years`: under 0.5 beginner, 0.5 to under 2 intermediate, 2 or more advanced (the 6-month and 2-year cuts above); ordinal = max(history, self); `experience.source` is `intake` only when the self-report is strictly higher, else `history`. The intake keeps three inputs (T-198): years 0-60, known maintenance 1 200-6 000 kcal and free text <= 500 characters, enforced by the table and `save_coach_intake`, which writes only the keys it receives. **Situation (removed by T-198):** no situation is stored or derived any more; the first phase of a plan comes from the intention only, and the pause after 28 days without a session (T-189) and the return-load rule (T-192) read the session dates directly. **Expenditure prior:** when the diary is not reliable and `known_maintenance_kcal` is set, `total_expenditure` is that value with source `intake`, provisional, and `profile_data` is no longer missing; the diary stays flagged unreliable and calorie changes stay off. When the adaptive expenditure qualifies it takes over; `handover` is true until the user saw the one-time card (`maintenance_handover_at`). The free text feeds no calculation; it reaches the plan and the block requests as context only (§7.8, ADR-87).
- **7.6 Confirmation and re-ask.** `confirm_derived_values` recomputes everything on the server and stores `estimate` and `uncertainty` per key that has an estimate (a trend without slope or an expenditure without data stays unconfirmed). With `p_activity_level` it stores that level (`edited`), else the estimated one; the expenditure stored uses the confirmed level. A confirmed value is **re-asked** when `abs(new − stored) > stored uncertainty` (strictly; on the edge it stays confirmed); a re-asked value reports the new estimate with `confirmed = false`. `provisional = not confirmed`. One band of activity (0.175) re-asks a value confirmed with data (0.1) but not one confirmed profile-only (0.2).
- **7.7 Examples.** 4 999 steps sedentary, 5 000 light; male, 26, 178 cm, 74.2 kg, moderate: BMR 1729.5, TDEE 2681; 60 % logged days (17 of 28) unreliable, 20 of 28 reliable; e1RM 100 × 5 = 116.5 (§4.1); 3 sessions per week bump 5 000 steps (light) to moderate, 2 do not.
- **7.8 Coach summary.** `coach_summary(p_today)`: exactly 8 ISO weeks (oldest first, empty weeks keep the shape). Per week: weigh-in average and days, logged diary days, mean kcal and macros of logged days, steps, active kcal, sleep minutes (average per night), completed sessions, working sets per primary muscle group (cardio excluded, at most 8 groups, §4.6 filter), cardio sessions and minutes, check-in energy. Top level: profile (sex, age, height, latest weight), training preferences, the estimates object (T-180 adds `total_expenditure.slope_used` / `anchor_kcal`, `weight_trend.weigh_in_days`, `intake.mean_kcal` / `anchor_kcal`), at most 12 main lifts (movement patterns of `07` §3, by sessions then key) with weekly best e1RM, at most 10 open discomforts (exercise, level, date). No free text and no raw rows. Hard cap 16 384 bytes. **Amended 2026-11-01 (ADR-87, `07` §8; detail in T-185):** "no free text" is void: the summary adds one block "Lo que el entrenador sabe de ti" with the intake free text (≤ 500 characters) and the check-in notes, discomfort notes and "¿Cómo te ha ido?" answers of the last 8 weeks, newest first, verbatim, cut at 2 000 bytes in total, minus the lines the user left out; set and routine notes, food names and custom exercise names stay out; still no raw rows. **Rules as built (T-185):** lines come from the intake text (always, dated by `saved_at`), `weekly_check_ins.notes` (week start from `coach_week_start(p_today) - 49` to `p_today`) and `exercise_discomforts.note` (same window by `logged_at`, resolved ones included); `review` answers join in T-190. Ordered newest first (ties: kind, source id). Budget: the byte size of the JSON-escaped text (so multi-byte characters count as bytes), lines accumulate from the newest while the total stays <= 2 000 bytes (`sent`); the line that crosses it and every older one are `over_limit` (strict prefix, a line is never truncated); at most 20 lines are sent; lines the user left out (`excluded`) consume nothing. The worst case measured by pgTAP (20 lines of 100 escaped bytes, all 8 weeks, 12 lifts, 10 discomforts) is 14 158 bytes, under the 16 384 cap. **T-198:** the `plan_block` request carries the same free-text block as `plan_nutrition`, under the key "Lo que el entrenador sabe de ti" (the lines with status `sent`, newest first, at most 2 000 bytes, absent when there is none), with the context-only sentence in its system prompt: it never changes a figure or the candidate list.
- **7.9 Plan and block inputs (T-175, US-78).** `coach_plan_inputs(p_kind, p_today)` (`plan` or `block`, `22023` otherwise) is the one list of what a plan or block reads; the `coach` function refuses with `coach_missing_data` using exactly its blocking `missing` keys. Read-only; reuses `coach_compute`. Each entry: `key`, `value`, `source` (`profile`, `my_training`, `weigh_in`, `coach_estimate`, `intake`), `status` (`ok`, `missing`, `unset_optional`, `provisional`, `stale`), `blocking`, `fix_target` (`my_training`, `personal_data`, `weight`, `activity_sheet`, `intake`; null for derived values), `date` (weigh-in only); plus `current_plan` (`accepted` wins over `proposed`; absent when none). **T-198:** the intake entries `training_years`, `known_maintenance` (plan only) and `free_text` are always `ok` or `unset_optional` and never blocking (R-53).
  - **Plan keys:** `intention` (missing blocks), `sex` (missing blocks), `age` and `height` (missing; block only when total expenditure has no value, so users on the adaptive path keep working; since T-180 a reliable diary alone makes the path adaptive, so those users are no longer blocked by age or height), `weight` (last weigh-in; none blocks; older than 14 days from `p_today` is `stale` and does not block, exactly 14 days is `ok`), `activity_level`, `total_expenditure` (missing never blocks by itself, its roots do), `weight_trend`, `diary` (the last three are `provisional` until confirmed or when data is insufficient, never blocking).
  - **Block keys:** `intention` and `place` (missing blocks), `equipment` (lifting values only; empty is `unset_optional`), `cardio` (T-184: the cardio machines selected, always `ok`, never blocking, empty means the coach proposes walking), `days_per_week` and `session_minutes` (null is `unset_optional`), `experience` (`provisional` until confirmed). Entries the user can edit keep their `fix_target` whatever their status.

## 8. Coach nutrition (E13, T-161, [coach design](07-coach-design.md) §4, §6, §9)
The server computes every figure in TypeScript (`nutritionRules.ts`); the model only chooses outcomes among server-built candidates and writes their reasons and deadlines. Inputs: intention (`training_preferences`), sex, latest weight, `total_expenditure` (§7.2) and experience (§7.5), all from `coach_summary`; the client sends only its date. Missing sex, weight, expenditure or intention: `coach_missing_data`.
- **8.1 Rate.** Percent of body weight per week. `fat_loss`: loss 0.5 (default; range 0.5-1.0). `muscle`: gain by experience, beginner 0.5, intermediate 0.35, advanced 0.25 (range 0.25-0.5). `strength`, `recomposition`, `maintenance`: rate 0 and adjustment 0 (*design decision*, `07` §9).
- **8.2 Calories.** `delta = ceil(rate × weight_kg × 11 / 10) × 10` kcal/day (`11 = 7 700 / 7 / 100`; rounded up to 10 so the rounded rate never falls under the range minimum, so the effective rate can sit up to about 0.01-0.05 points above the aimed one). Loss: `target = expenditure − delta`; gain: `expenditure + delta`; with an intake anchor the target is also checked against the rate (§8.7). Limiters in order: `delta` capped at 500 (loss; amended 2026-11-01 from 1 000, `07` §4 deficit cap, Murphy & Koehler 2022) / 750 (gain), `limited_by = goal_range`; then the floor 1 200 (women) / 1 500 (men) (ADR-25), `limited_by = floor`, which wins over the cap note. A loss with the expenditure at or below the floor has no deficit to give: `coach_plan_infeasible`. `calorie_adjustment = target − expenditure` (inside the `nutrition_goals` range by construction); `strategy` deficit / maintenance / surplus by its sign. `rate_kg_week = adjustment × 7 / 7 700` (signed: loss negative, gain positive); `rate_pct_week` is the same in percent of body weight, positive in the direction of the intention (slower than aimed under a limiter).
- **8.3 Macros.** Protein g/kg: deficit with intermediate or advanced experience 2.2, deficit with beginner 2.0, recomposition 2.0, others 1.8 (always within 1.6-2.2). `protein_pct = ceil(protein_g_per_kg × weight × 4 / target × 100)`, fat 25 %, carbohydrates the rest (§1.5: integers in 5..90 summing to 100, grams `round(target × pct / 100 / kcal_per_gram)`). If carbohydrates fall under 5 %, fat goes to 20 %, then protein to 1.6 g/kg; still under 5 %: `coach_plan_infeasible`. Because the percentage is rounded up, the stored grams can sit a few grams above `g/kg × weight`. Protein guidance (no foods, no times): `per_meal_g = round(0.4 × weight_kg)` over at least 4 meals.
- **8.4 Outcome candidates.** Built from the summary, never by the model: `weight` (only `fat_loss` and `muscle`): `round(weight_kg + rate_kg_week × 4, 1)`; `e1rm:<lift key>` for each main lift with weekly best e1RM in at least 3 of the 8 weeks and a positive least-squares slope: `round(last e1RM + slope × 4, 1)`. Body fat and circumferences are not in the summary, so they are not candidates yet. **No model (T-218, ADR-98):** `plan_nutrition` builds the outcomes by rule (`outcomeTemplates.ts`): the `weight` candidate first, then the `e1rm` candidates ordered by weeks with data (desc), logged sessions (desc), exercise key (asc), at most 3 (so at most 4 outcomes); deadline = block start + 28 days; Spanish template reasons: weight cut "Perdiendo unos {r} kg por semana, en 4 semanas llegarías a {t} kg.", weight gain "Ganando unos {r} kg por semana, en 4 semanas llegarías a {t} kg.", e1RM "Tu levantamiento sube unos {s} kg por semana en las últimas {n} semanas; si sigues así, {t} kg." (decimal comma, at most two decimals; the e1RM reason does not name the exercise: the server has no Spanish catalogue names, and the outcome's key identifies the lift). The kind is `deterministic`: same input, same output, answered before the provider and budget checks, no usage row; the saved `method` is `{model: null, attempts: 0, cost_eur: 0, constants_version}`. Final server check (`assertNutritionInvariants`): rate ranges (a slower rate only with `limited_by`), floor, protein 1.6-2.2 g/kg, fat 20-35 %, percentages, grams, guidance; a failure is `INTERNAL` and nothing is stored (unreachable by construction).
- **8.5 Acceptance and calorie changes.** `propose_coach_plan` stores the plan as `proposed` (an older proposal becomes `superseded`, its recommendation `discarded`). `requires_confirmation = true` with `unconfirmed[]` when any of activity level, expenditure (with a value), experience or the weight trend (with a slope) is provisional (§7.6); the plan is shown, but `accept_coach_plan` fails with `55000 derived values unconfirmed` until the values are confirmed. Accepting supersedes the previous accepted plan and upserts `nutrition_goals` from the plan (later Preferencias saves count as manual edits: `edited_by_user`, E13 Q8). **Calorie proposals the user approves (T-229, US-99; amended 2026-11-05, `07` §4; this replaces the "applies on its own" / "Deshacer" text of 2026-11-01 and the `edited` decision).** `evaluate_coach_calorie_change(p_today)` returns `{status: created|pending|none, reason, recommendation_id?}` and checks in this order, each a distinct `reason`: (1) `edited`: no accepted plan or the plan is `edited_by_user` (a plan with no saved block still proposes, §9.15); (2) `already_pending_this_week`: a pending proposal created this week is returned unchanged (`status: pending`; idempotent); (3) `declined_twice`: two `discarded` proposals of the plan since `block_start`; (4) `recent_change`: a proposal accepted or discarded in the last 14 days (`superseded` counts nowhere); (5) `missing_records`: `coach_week_gate` is not `ok` for the 7 days ending `p_today` or the 7 days ending `p_today − 7` (`complete_days >= 5` and `weigh_in_days >= 3`; a day is complete when its diary sum is at least 40 % of the median daily sum of the 28 days, §7.3); (6) `unreliable_intake` (§7.3, 20 of 28 days); (7) `inside_interval`: for both `p_today` and `p_today − 7` the weight trend has an interval and the plan's `rate_kg_week` is strictly outside it on the same side (on the edge counts as inside, §7.6). Size `abs(slope − rate_kg_week) × 1 100` kcal/day (7 700 / 7), rounded to 10, at least 50, at most 10 % of the target (rounded down to 10; `07` §4). Target under the interval: fewer calories; over it: more. Safe band, all must hold or no proposal is made (`reason` `floor`, `deficit_cap`, `rate_range`, `band`): new target at or above the floor (ADR-25); `calorie_adjustment` in [−500, 750] (`deficit_cap` below, `rate_range` above); the target against the expenditure in use (§7.2) inside the range of the plan's phase (§8.7, §8.9: cut 0.5-1.0 %/week, gain 0.25-0.5, maintenance and recomposition the no-change range), where a limiter (`limited_by`) may make a plan slower than the range, never faster, and a change that moves the target toward the range is never refused for starting outside it (a gaining maintenance user does get a decrease); and the accepted changes of the block (since `block_start`) plus this one add up to at most ±10 % of the block's accepted calories (plan target minus those changes; declined and superseded proposals do not count). A pending proposal that stops qualifying stays until the user decides or a newer proposal replaces it (the older one becomes `superseded`; never two `pending`, unique index). Payload: `from_kcal`, `to_kcal`, `change_kcal`, `change_pct`, `slope_kg_week`, `interval_low`, `interval_high`, `rate_kg_week`, `base_kcal`, `band_used_kcal`, `weeks: 2`. `decide_calorie_proposal(p_id, p_apply)`: `true` ("Aplicar") applies `to_kcal`, keeping the protein grams and the fat percentage, recomputing `protein_pct` (rounded up) and carbohydrates, updating `nutrition_goals` and the plan JSON (`calorie_changes` + 1) without setting `edited_by_user`, and stores `accepted`; `false` ("Ahora no") stores `discarded` and changes nothing. The typed-kcal `edited` decision (±10 % of `from_kcal`) was removed. A week with fewer than 5 complete diary days or fewer than 3 weigh-ins changes nothing ("Esta semana faltan registros: no cambiamos tus calorías."). Data cleaning: partial days (under 40 % of the 28-day median, §7.3) are excluded from every count. Phase calories (cut, minimal, maintenance after a cut): `07` §4 and §12.3 (T-187).
- **8.6 Examples.** (a) `fat_loss`, male 80 kg, expenditure 2 600, intermediate: delta 440, target 2 160, rate 0.5 %/week (−0.4 kg), protein 2.2 g/kg, 33 / 42 / 25 % = 178 / 227 / 60 g, 32 g of protein per meal. (b) Female 50 kg, expenditure 1 500: delta 280, target 1 220, floor not hit. (c) Female 50 kg, expenditure 1 400: raw 1 120, target 1 200 (`limited_by floor`), effective rate 0.364 %/week (slower). (d) `muscle`, male beginner 70 kg, expenditure 2 500: delta 390, target 2 890 (0.506 %). (e) 75 kg: 30 g of protein per meal over 4 meals. (f) `fat_loss` 120 kg, expenditure 3 000: 0.5 % gives 660, capped at 500 (`goal_range`, slower rate 0.38 %/week); aiming 1.0 % (1 320) is capped at 500 too. (g) Plan target 2 200, rate −0.4 kg/week, weight flat with interval [0, 0] for two consecutive weeks: change −220 (10 % cap, instead of 440), to 1 980; protein 176 g kept: 36 % protein, 25 % fat, 39 % carbohydrates; the next change can come 14 days after the decision.

- **8.7 Target check against the intake (T-180, ADR-84).** With `d(r) = r × weight × 11` kcal/day and `shift = expenditure − anchor_kcal` (the clamped slope term, 0 when `slope_used` is false), the allowed `target − anchor_kcal` is: `muscle` `[shift + d(0.25), shift + d(0.5) + 10]`; `fat_loss` `[shift − d(1.0) − 10, shift − d(0.5)]`; `strength`, `recomposition`, `maintenance` `[shift − d(0.25), shift + d(0.25)]` (the 10 kcal is the rounding of §8.2). A limiter (`floor`, `goal_range`) may make a plan slower than the range, never faster; for the no-change intentions only the floor may lift the target above it. `computeNutrition` never produces an out-of-range target and `assertNutritionInvariants` rejects one (`target_above_intake_range`, `target_below_intake_range`, `slope_term_range`; `INTERNAL`, nothing stored). Skipped without an anchor (formula path, plans stored before T-180). The plan JSON gains `intake_anchor_kcal`, `slope_used`, `slope_term_kcal` (`expenditure_kcal` is the anchor plus that term). Examples at 80 kg: (a) the reported shape, intake 2 262, 5 weigh-ins over 3 weeks: `slope_used` false, expenditure 2 262, beginner `muscle` target 2 702 (+440), not 2 972; (b) a brand-new user without a reliable diary: formula, no anchor, examples of §8.6 unchanged; (c) intake 2 262 with a trend of −0.6 kg/week over 4 weeks and 10 weigh-in days: expenditure 2 262 + 660 clamped to 2 702; (d) ranges at 2 262: `muscle` 2 482-2 712, `fat_loss` 1 372-1 822, `maintenance` 2 042-2 482.
- **8.9 Phases (T-187, ADR-86, [coach design](07-coach-design.md) §4, §12.3).** `plan_nutrition` starts the plan in the first phase and stores it: `nutrition.phase`, `phase_reason` (`intention`, `underweight`; the Spanish text is the client's) and `phase_options {cut_rate_pct, diet_break}`. First phase from the intention: fat loss cut, muscle gain, recomposition recomposition, maintenance and strength maintenance (T-200, ADR-91: no regain phase exists; a stored one reads as maintenance). Rate by phase: cut the chosen rate (0.5 default, 0.5-1.0, anything else `INVALID_INPUT`), gain by experience, maintenance, recomposition and minimal 0. Limiters in order: the deficit cap (500 kcal, `limited_by = deficit_cap`), then the floor, which wins. The no-change range of §8.7 is chosen **by the phase**, not by the intention. `assertNutritionInvariants` and `coach_assert_plan` (same rules, `22023`): adjustment in -500..750; `deficit_cap` (a deficit above 500), `deficit_cap_flag` (the flag needs a cut and exactly -500); cut: `loss_needs_deficit`, rate 0.5-1.0 (slower only with a limiter); gain: surplus, rate 0.25-0.5; maintenance, recomposition, minimal: `no_change_range` (at most 0.25 x weight x 11 + 10 kcal either way); `diet_break`, `diet_break_phase` (the maintenance week only on a cut with the option on); `phase`, `phase_reason`, `phase_options`. **Input bounds and underweight stop (T-218, [coach design](07-coach-design.md) §4):** age 18-100, height 120-230 cm and weight 30-300 kg; a present value outside its bounds is treated as missing (`coach_missing_data`, root cause `age`, `height` or `weight`); an absent age or height is not refused by the function (the shared list decides). With BMI = weight / (height/100)² below 18.5, an intention of fat loss and no fixed phase, the plan starts in maintenance with `phase_reason = underweight` (the client shows the note `underweight_no_cut` from the reason; a maintenance plan has no cut options, so no recompute). BMI 18.5 stays a cut; other intentions are unchanged. `coach_assert_plan` and the `coach_plans_phase_reason_values` check accept `underweight`. **Choosing how fast to cut and the diet break** (`plan_recompute`, no model, no usage, answered before the budget check): input `{today, plan_id, cut_rate_pct, diet_break}` of a proposed cut; the server recomputes with the current summary, keeps the plan's own cardio edit, and `update_coach_plan_options` rewrites the plan and drops the `weight` outcome (its target is weight + rate x 4 and its reason cites the old figure; the `e1rm` outcomes stay). `plan_nutrition` accepts the same two options. **Accepting a phase change at the review** uses the sibling kind `plan_phase_change` (§8.10). **Diet break:** `nutrition.diet_break` holds the week-4 figures at rate 0 (macros included); `apply_coach_diet_break(today)` (run when the Trainer opens) sets `nutrition_goals` to them in plan week 4 and back to the base figures in any other week, without marking the goal as edited by the user; skipped for a plan the user edited, without a saved block or without the option. Weeks count as in §9.9 (calendar weeks from `block_start` until T-189). **Minimal (removed 2026-11-03, E13 Q56, T-205/T-206; void below):** "Tengo poco tiempo" (`plan_block` with `minimal: true`) makes the block's phase minimal and leaves the plan's calories as they are (the calorie change belongs to the review, T-190). **Examples (80 kg unless noted):** (a) cut 0.5 % at 120 kg, expenditure 3 000: 660 asked, target 2 500, `deficit_cap`, rate 0.379 %/week; (b) 80 kg at 1.0 %: 880 asked, 500 given, target 2 100 at expenditure 2 600; (c) a floor case is still `floor`; (d) diet break at expenditure 2 600: weeks 1-3 target 2 160, week 4 target 2 600; (e) minimal: 1 set per previous main lift (2 from 65), cardio 100 min with 1 routine = 30 + 70 por tu cuenta, 2 routines = 30 / 30 + 40.
- **8.8 Activity targets (T-181, ADR-85, [coach design](07-coach-design.md) §3).** `plan_nutrition` also stores `nutrition.activity` (`data_version` stays 1; plans stored before T-181 lack it) = `{cardio_min_week, cardio_edited, cardio_band, steps_day, steps_basis, steps_avg}`, from `cardioRules.computeActivity` (pure, no age input) and independent of the calories (Q25). Cardio is 150 min/week for every intention (`cardio_band` [150, 300] only for `fat_loss`, else null). `steps_day = max(floor(steps_avg / 500) * 500, 7 000)`; `steps_avg` is the 28-day average (`estimates.activity_level.sources.steps_avg`, null under 7 days of data) and no data gives 7 000 with `steps_basis = floor`; otherwise `average`. `assertActivityInvariants` rejects cardio other than 150 (100 in the minimal phase, amended 2026-11-01, §9.11), steps under 7 000, under the average rounded down to 500, or not a multiple of 500 (`INTERNAL`, nothing stored). The model never writes these figures; the reasons are static client copy. The user edits only the cardio, through `set_coach_plan_cardio(p_plan_id, p_minutes)` (planner proposal): plan owned by the caller with status `proposed` or `accepted` (`P0002` otherwise), minutes an integer 0..600 in steps of 5 (technical bounds, `22023`), a plan without `activity` refused (`22023`); it sets `cardio_min_week` and `cardio_edited = true` and nothing else. Steps are not editable. Examples: average 7 740 -> 7 500 `average`; 6 740 -> 7 000 `floor`; no data -> 7 000 `floor`; edit 150 -> 90 keeps `target_kcal` identical.
- **8.10 End-of-block review and phase change (T-233, US-101, US-103, [coach design](07-coach-design.md) §5, §6, §12.3-12.4).** The accepted plan's block ends on `coach_block_end` = start + 7 x last plan week - 1 (calendar weeks, as §9.9). "Seguir como estoy" = `keep_coach_phase`: `kept`, no plan; the proposal is offered again at the next review if the data still say so. A second decision is `55000`.

Outside any week, another routine or no free row: nothing. A missed session is never moved or relinked; deleting the workout empties `session_id`. `coach_plan_weeks(plan, today)` returns per week `planned`, `completed`, `adherence_pct = round(completed * 100 / planned)` half up (3/4 = 75, 1/3 = 33, 2/3 = 67), `phase` (`past|current|upcoming`) and the sessions with `done`; only weeks that have sessions are returned. Cardio and steps per week (T-183): `cardio_min_done` = round half up of the summed `duration_s / 60` over the week (not per set) of completed sets of `completed` sessions whose exercise has `movement_pattern = 'cardio'` (any cardio, planned or not), by the same UTC date window; nothing carries over. `cardio_min_target` = `nutrition.activity.cardio_min_week`, else `training.cardio.target_min_week`, else null. `steps_avg` = rounded mean of `daily_activity.steps` over the week's days that have steps (null without any); `steps_target` = `nutrition.activity.steps_day` or null. **Amended 2026-11-01 (ADR-86, `07` §12.5; detail in T-189):** weeks follow the training, not the calendar: a calendar week (ISO, Monday-Sunday) with no completed session does not count as a block week; the block pauses and resumes at the next planned session, so plan week `n` is the `n`-th calendar week with a completed session since `block_start` (the current week is the next one), and the end of the block, the end-of-block review and the deload evaluation (§9.10) move with it.
- **9.10 Deload suggestion (T-165, US-75).** `evaluate_coach_deload(today)` (idempotent) looks at the current plan week `c` of the accepted plan with a saved block. Reason codes in order: `no_block`; `too_early` (`c < 3`, or `c` is the last week of the saved block, so a 4-week block can only get a deload in week 4, evaluated in week 3); `already_decided` (a deload for week `c + 1` exists and is not pending; a pending one is returned as `pending`); `no_main_lifts` (no squat, hinge, lunge, push or pull exercise with a completed set, warm-ups per `warm_up_included()`, in each of weeks `c-2..c`); `improved`. With best e1RM per week `w1, w2, w3` (all completed workouts, not only linked ones), a lift improved iff `max(w2, w3) > w1` (strict: a tie is not an improvement); if any lift improved there is no deload, otherwise a `deload` recommendation for week `c + 1` is created. `decide_coach_deload(id, accept)`: accepting sets `deload = true` on that week's plan sessions (routines are never rewritten), discarding changes nothing else. `deload_suggestions(session)`: in a deload week, for the routine's session, `deload_sets = max(1, round(0.6 * working sets))` (1, 2, 3, 4, 5, 6, 8, 10 give 1, 1, 2, 2, 3, 4, 5, 6), same weights. **Amended 2026-11-01 (ADR-88, `07` §3; detail in T-193):** the deload **applies on its own** (no pending recommendation), shown with its reason and "Cancelar descarga"; it is triggered as above or **scheduled** in week 4 of a block when no deload ran in the previous 7 training weeks (plan weeks of §9.9: paused calendar weeks do not count; not in the minimal phase); at most one deload per block, always week 4; after a week-4 deload the review's e1RM trend uses weeks 1-3; outside a deload the user can start one for the next week ("Hacer descarga la próxima semana"). Week `c` is the plan week of §9.9 (paused weeks do not count). **As built (T-230, US-100; supersedes the T-165 reason codes, `decide_coach_deload` and the pending recommendation above):** `evaluate_coach_deload(today)` applies in plan week 4 only (`c = 4`, block of at least 4 weeks): with the weekly best e1RM `w1, w2, w3` of weeks 1-3 it is **triggered** when at least one main lift has all three and none improved (`max(w2, w3) > w1`), else **scheduled** when at least 7 training weeks passed since the last deload week; a training week is a plan week (any block of the user, current weeks 1-3 included) with a completed workout in its dates, so a week without one does not count. It sets `deload = true` on that week's plan sessions and writes a `coach_changes` row (`deload_triggered|deload_scheduled`), once per block: any deload row of the plan, cancelled included, or a deload mark makes later calls return `already_applied`. Reduced sets and weights are unchanged (`deload_suggestions`). `cancel_coach_deload(change)` sets the week back to normal and the row to `undone` (a second cancel is refused). `request_coach_deload()` marks the next plan week (`deload_user`) only when no deload is planned or ran in the block (after a cancel the user may ask again). "Eliminar bloque" detaches the deload rows from the plan. No model call.

- **9.15 Block lifecycle (T-202, ADR-94; T-203, T-204, T-206, T-208).** "Crear bloque" asks "Desde cero" or "Desde una carpeta" (§9.2, §9.14); a plan with a saved block offers "Eliminar bloque" instead of "Crear bloque". **"Eliminar bloque"** removes the block from the plan without a new plan: the plan's nutrition, phase and activity targets stay; plan weeks, links and the block's deload marks go (E13 Q54, user 2026-11-03); the block's folder and routines stay in Entreno as normal routines and workouts are untouched; without a block there are no plan weeks, deloads, automatic load changes or end-of-block review, while calories, Diario and the weekly report keep running and automatic calorie changes keep applying inside the safe band (E13 Q58 recommendation); a later "Crear bloque" on the same plan starts its plan weeks on the day of its "Guardar bloque". **Transparent block:** saved block routines are the user's; editing them in Entreno keeps the plan links (by routine id); the next block may start from that folder and so reads the edits. **Favourites:** `exercise_favorites` per user and exercise (catalogue or custom); first in the exercise picker and the preview swap list (a stable partition: favourites first, then the existing order; the picker stays filter-only and name-sorted within each group; a favourite that is not an alternative never appears in the swap list); preferred by the model within group or pattern after the hard checks, never forced, never extra volume. **As built (T-206):** `plan_block` stores three additive keys inside `coach_plans.training` (jsonb) before the block is attached, so the preview reloads them after process death: `split_reason` (string), `changes_vs_last_block` (string or null when there is no previous block) and `notes` (string list, e.g. `below_recommended`). `BlockTraining` reads them with defaults, so older blocks still decode. The splits screen owned both paid calls (`block_splits`, then `plan_block` with the chosen split; both removed in T-224, ADR-99); the preview only reads the stored block.
- **9.16 Nothing applies by itself after the block (T-233, US-101, US-103).** After `coach_block_end` and until the review is decided: `evaluate_coach_calorie_change` proposes nothing (`reason = block_ended`; a plan with no saved block still proposes, §8.5), `apply_coach_progression` writes nothing for a session that started after the last day, `evaluate_coach_deload` and `request_coach_deload` already refuse (`past_week_4`, `coach_deload_no_next_week`), and `apply_coach_diet_break` leaves `nutrition_goals` as it is (no revert to the base figures). What the user taps stays allowed (`decide_progression_flag`, `undo_coach_change`, `decide_calorie_proposal` on a proposal already pending). The review itself is §8.10.
- **9.17 The next block in the builder (T-235, US-102, `07` §3 "Block builder" (e)).** "Crear el siguiente bloque" opens the builder pre-filled with the last block (split, day types, exercises still eligible, loads from history) after a step "Objetivo por grupo". Per H1 group: base = the previous block's weekly sets (10 for a first block); "Priorizar" = base + 2 (cap 20) only with adherence >= 80 % and not a cut; "Mantener" = 4 (6 from 65); the sets freed by "Mantener" go first to prioritised groups, +2 each in group order, up to 20, the rest unused; at most three "Priorizar" (the fourth is disabled with "Ya priorizas tres grupos."); with adherence < 80 % or null no own +2 ("Tu adherencia fue menor del 80 %: no añadimos series."); in a cut only freed sets ("En definición solo recibe las series que liberes con Mantener."). Examples: base 10 + Priorizar Hombros at 85 % -> 12; base 19 -> 20; Mantener Bíceps at 66 years frees 4 instead of 6; at 70 % a prioritised group still receives freed sets. "Sugerencia: +2 series" is offered on a stalled group with adherence >= 80 %, no open discomfort, no cut, target + 2 <= 20 and no "Me ha costado"; it changes nothing until tapped, a second tap undoes it. Main lifts that stalled show "puedes cambiarlo" with a `?`. Saving goes through `save_built_coach_block`; no model call.
