# Data model (Supabase Postgres) - current state

Compact summary; full column tables, constraints and RPC contracts are in [`phase1/03-data-model.md`](phase1/03-data-model.md) (frozen). The authoritative schema is `supabase/migrations/`. New schema decisions: a new ADR in `00-decisions.md`, then update this summary.

## Conventions
- All tables in `public`; `id uuid` PK default `gen_random_uuid()` unless stated; `created_at` and trigger-maintained `updated_at`.
- `user_id uuid not null default auth.uid() references auth.users(id) on delete cascade` (every user-owned table cascades; ADR-29). Nullable author columns pick `cascade` or `set null`.
- RLS enabled and forced on every table; owner policy `user_id = (select auth.uid())` for select/insert/update/delete. Closed value sets are Postgres enums.
- Calendar dates (`log_date`) are `date` in the device's local time zone; instants are `timestamptz`.
- No default privileges for `anon`; every new object needs an explicit grant to `authenticated`/`service_role`.

## 1. Enums
`sex`, `activity_level` (sedentary..very_high), `goal_strategy` (deficit/maintenance/surplus), `meal_type` (default meal codes), `food_source` (off/user), `food_base_unit` (g/ml), `food_cooking_method` (raw/griddle/air_fryer/fried), `measurement_source` (manual/health_connect), `circumference_site`, `muscle_group` (chest, back, shoulders, biceps, triceps, forearms, quads, hamstrings, glutes, calves, core, full_body, adductors (T-211: hip adduction, outside H1)), `equipment`, `session_status` (in_progress/completed/discarded), `exercise_metric_type` (weight_reps, reps_only, duration, weight_duration, distance_duration, bodyweight, assisted, weighted, steps_duration, floors_duration), `set_type` (working/warm_up/failure/drop), `notification_kind` (weight/circumference/weekly_check_in), `coach_value_key` (activity_level/total_expenditure/weight_trend/experience, T-157).

## 2. Profile and goals
- `profiles` (id = auth user): display_name, avatar_url (Google, `https://` only), birth_date, sex, height_cm, activity_level, onboarding_completed (the former `target_weight_kg` was dropped in T-162, ADR-78: the weight outcome now lives in the accepted `coach_plans.outcomes`). Created by the `on_auth_user_created` trigger (sanitized metadata); `on_auth_user_metadata_updated` refreshes the avatar only. Client has SELECT and column-level UPDATE; no delete. Current weight is the latest `body_measurements` row.
- `nutrition_goals` (one per user): strategy, calorie_adjustment, target_kcal, protein/carbs/fat percentages. Written together with `profiles` through `save_preferences`.

## 3. Nutrition
- `foods`: source (`off`/`user`), barcode, off_id, base_unit, nutrition per 100 base units (kcal, macros), `micronutrients jsonb` (35 label keys), `off_data jsonb` (full OFF product, Edge-Function-written only), serving fields, image_url, created_by, `search_vector`, `fetched_at`. Shared cache for OFF rows; manual foods are owner-only (editable, ADR-53).
- `food_portions` (food_id, label, amount in base units, position).
- `food_log_entries`: log_date, meal_slot_id, food_id, resolved `amount`, `portion_label`, snapshots of kcal/macros/`food_name`, `cooking_method`, `cooking_oil_retained_g` (added fat g), nullable `group_id`/`group_name` (saved-comida group snapshot, ADR-68).
- `meal_slots` (label, position, `enabled` always true; deleted when unused, at least one stays; ADR-41). Seeded Desayuno/Comida/Merienda/Cena at onboarding.
- `meal_templates` ("comidas", unique name per user, suggested slot nullable) + `meal_template_items` (food, amount, portion, cooking_method).
- `food_preferences` (one per user): fat % for griddle / air fryer / fried (0-20).
- `meal_defaults` (user, meal_slot, template, ISO weekday; one per slot+weekday) and `diary_default_applications` (user, log_date marker; idempotent daily apply).
- `favorite_foods` (user, food).

## 4. Weight
- `body_measurements`: measured_at, weight_kg, body_fat_pct, lean_mass_kg, water_kg, bone_kg, bmr_kcal (composition only from Health Connect), source, `external_id` (HC dedup), `hc_record_id` (copy written by the app). The onboarding weight is the user's first row.
- `body_circumferences` (site, value_cm, measured_at). `health_sync_state` (last sync per user; `last_auto_sync_date` date, nullable, written only by `mark_health_auto_sync`).
- Watch data (T-140, [E11](epics/E11-health-connect-daily-sync.md)), all owner-only (RLS enabled and forced, select/insert/update/delete own with `(select auth.uid())`, `on delete cascade` from `auth.users`):
  - `daily_activity`: unique `(user_id, day)`, `steps` 0-1000000, `active_kcal` and `total_kcal` numeric(8,2) 0-100000, all value columns nullable.
  - `sleep_sessions`: unique `(user_id, external_id)`, `started_at`, `ended_at` (> started_at), `minutes` 1-1440, `stages` jsonb array (`[{stage, started_at, ended_at}]`).
  - `resting_heart_rate`: unique `(user_id, day)`, `bpm` 20-250, `external_id` (informational).
  - RPC `import_health_activity(p_daily, p_sleep, p_resting_hr) -> {daily, sleep, resting_hr}` (rows written; max 400 per array, `22023` otherwise; upserts, last duplicate wins; does not touch `health_sync_state`). RPC `mark_health_auto_sync(p_day)` upserts the state row and sets only `last_auto_sync_date`. Both `security invoker`, `authenticated` only.
- `notification_settings` (T-135, US-57): `(user_id, kind)` primary key (`kind` enum `notification_kind`: `weight|circumference|weekly_check_in|week_summary`, the last since T-231), `enabled`, `updated_at`; owner select/insert/update (no delete), client upserts on `(user_id, kind)`. **A missing row means enabled.** Reminders are derived on the client from the latest weight and circumference rows, never stored.
- `coach_block_reviews` (T-233, `04` §8.10): one row per plan (unique `plan_id`), `user_id` and `plan_id` cascade, `ended_on`, `inputs` (jsonb object `{adherence, lifts, groups, weight, outcomes, waist, stalls}`, frozen when the review opens), `phase_proposal` (null or `{to_phase, reason, figures}`), `phase_decision` (`accepted` or `kept`) with `decided_at` (both null or both set; a decision needs a proposal), `next_plan_id` (the proposed plan that "Aceptar" built; `on delete set null`), `created_at`; index `(user_id, created_at desc)`. RLS enabled and forced: owner select only, no client write. RPCs (all owner-scoped, `authenticated` only, `anon` revoked): `coach_block_end(p_plan_id) -> date` (invoker, stable: `coalesce(training_start, block_start) + 7 * max(week) - 1`, null without sessions; the one definition of the block's last day), `open_coach_block_review(p_today) -> jsonb|null` (security definer, idempotent: null unless the accepted plan has a saved block and `p_today` is after its last day; the first call stores the review through the internal `coach_block_review_build`, later calls return the stored row unchanged), `keep_coach_phase(p_review_id)` (security definer; stores `kept`, builds no plan), `accept_coach_phase(p_review_id, p_nutrition, p_outcomes, p_method, p_input_summary, p_block_start default today)` (security definer; the phase of `p_nutrition` must equal `phase_proposal.to_phase`; delegates to `propose_coach_plan`, which supersedes any older proposal, then stores `accepted` and `next_plan_id`; returns `{review, plan_id}`). Errors: `28000` not signed in, `P0002` unknown or foreign review, `22023` invalid or phase mismatch, `55000` no proposal or already decided. `muscle_group_sets` gained an explicit owner filter (same result for the caller; correct also inside a security definer function). Guards after the block's last day: see `04` §9.16.
- `coach_week_summary_seen` (T-231, `04` §6.7): `(user_id, plan_id, week)` primary key, `user_id` and `plan_id` cascade, `week` >= 1, `seen_at`. RLS enabled: owner select only; written by `mark_coach_week_summary_seen(p_plan_id, p_week)` (security definer, idempotent upsert, `P0002` for a plan that is not the caller's, `22023` for a week under 1). `coach_week_summary(p_today) -> jsonb|null` (stable, security invoker; same `p_today` rule as the coach RPCs): the latest `past` week of the accepted plan (`coach_plan_weeks`), null when there is none or the week has no completed workout, no weigh-in and no diary day (no fallback). Keys: `plan_id, week, start_date, end_date, seen, sessions_done, sessions_planned, groups [{muscle_group, sets}], weight {avg_kg, slope_kg_week, interval_low, interval_high, target_rate_kg_week}, complete_days, weigh_in_days, missing_records (coach_week_gate not ok), changes [coach_changes rows created in the week], calorie_proposal {id, status, reason, payload, created_at, decided_at}|null, deload, stalls` (T-232: the elements of `coach_stall_diagnosis(plan, week)` for lifts not already stalled at the previous plan week, `[]` when none). `coach_stall_diagnosis(p_plan_id, p_week) -> jsonb` (stable, security invoker, scoped to `auth.uid()`; `[]` for a plan that is not the caller's): one element per main lift stalled over the last 3 plan weeks done up to `p_week` (`coach_stalled_lifts(p_plan_id, p_week) -> (lift_id, week_starts)`: non-deload weeks with a completed workout, weekly best e1RM, stalled iff not `max(w2, w3) > w1`), `{exercise_id, cause: sessions|sets|maintain|protein|sleep|none, ...figures}` with `avg_sessions` + `plan_days`, `avg_sets` + `group`, `group`, `avg_protein_g` + `protein_g_per_kg` + `target_g`, `avg_sleep_h`, or `protein_gate_missing`. No table. `muscle_group_sets(p_from, p_to, p_strength_only)` is the one set-counting implementation (the two-argument statistics function calls it with false); with true only H1-counting exercises (`counts_as_strength`, custom exercises unless time- or distance-based) count.
- `exercise_discomforts` (T-147, US-67): `id`, `user_id` (default `auth.uid()`, cascade), `exercise_id` (cascade), `logged_at`, `level` smallint not null (check 1-5, T-152/ADR-81; immutable after insert), `note` text 1-200 chars (nullable, never interpreted), `resolved_at` (check >= `logged_at`); index `(user_id, exercise_id, logged_at desc)`. RLS enabled and forced, owner select/insert/update, no delete (history for E13); update grant only on `resolved_at`. The 7-day open window is evaluated in the client. pgTAP covers isolation and constraints.
- `weekly_check_ins` (T-136, US-59): `(user_id, week_start)` primary key, `week_start` is an ISO Monday (check), `energy` smallint 1-5 (check), `notes` text <= 1000 chars, `created_at`, `updated_at` (trigger). RLS enabled and forced, owner select/insert/update (no delete), `(select auth.uid())`; pgTAP covers cross-user isolation.
- `coach_user_intake` (T-185, reduced by T-198; US-81, `04` §7.5; not `coach_intake`, that name is the diary-intake function): `user_id` PK (cascade, default `auth.uid()`), `training_years` numeric(4,1) 0-60, `known_maintenance_kcal` 1200-6000, `free_text` <= 500 chars, `maintenance_handover_at` (the one-time "your data takes over" card was shown), `saved_at`, `updated_at` (trigger). T-198 dropped `situation`, `injured_area`, `pre_break_bests`, `known_cut_kcal` and the types `coach_situation` and `coach_injured_area`. RLS enabled and forced, owner select/insert/update/delete, `(select auth.uid())`; removed with the account (cascade).
- `coach_free_text_exclusions` (T-185, US-89, `04` §7.8): PK `(user_id, kind, source_id)`, `kind` in `intake|check_in|discomfort|review`, `source_id` text 1-64 (`intake`; the check-in `week_start` ISO date; `exercise_discomforts.id`; `review` reserved for T-190), `created_at`. RLS enabled and forced, owner select/insert/delete (no update); cascade on the account. An exclusion never touches the source note.
- `profiles.check_in_weekday` (T-136): smallint 1 (Monday)-7 (Sunday), default 7, check 1-7; the only new column the client may update (column grant).

## 5. Training
- `exercises`: catalogue rows hold only `key`, `muscle_group`, `secondary_muscles`, `equipment`, `metric_type`, `per_hand`, `movement_pattern` (names/text/images come from the client bundle, ADR-38/39); custom rows (`is_custom`, owner) have a name. T-150 (ADR-78): `movement_pattern` is enum `movement_pattern` (squat, hinge, lunge, horizontal_push, vertical_push, horizontal_pull, vertical_pull, carry, core, isolation, cardio, other, shoulder_abduction (T-205: the 7 lateral-raise keys and the band-long copy of the cable one; an isolation role, not a main lift)), nullable; every catalogue knee-dominant compound is quads with `glutes` secondary and hip abduction/flexion/adduction are filed glutes/core/adductors (T-211, `07` §3 "Lower-body filing"); every catalogue hinge lists `hamstrings` as primary or secondary muscle (T-205, fractional volume count); `counts_as_strength boolean not null default true` (T-211, `07` §3 "What H1 counts") is false for stretches, mobility, cardio, impact moves and every timed hold (set from the generator's rule `render_strength_sql`) and is read by the coach's H1 count only, custom rows keep true (the coach decides them by metric type); every catalogue row is filled from the reviewed mapping `scripts/exercise-movement-patterns.csv` (generator checks coverage), custom rows may leave it empty and it is only data for the E13 coach (never shown on catalogue exercises). RPC `update_custom_exercise(p_id, p_name, p_muscle_group, p_equipment, p_per_hand, p_movement_pattern default null)` (security invoker, owner only; null clears the pattern). Creating a custom exercise is a plain insert that accepts `movement_pattern`.
- `exercise_favorites` (T-204, US-96): PK `(user_id, exercise_id)`, `user_id` default `auth.uid()` (cascade), `exercise_id` references `exercises` (cascade: deleting a custom exercise removes its star), `created_at`; index on `exercise_id`. RLS enabled and forced, owner select/insert/delete (no update); the insert policy also requires the exercise to be visible to the caller, so another user's custom exercise cannot be starred. The client upserts ignoring duplicates. `coach_summary` is unchanged; T-205 reads the table directly.
- `coach_folder_reviews` (T-207): **dropped in T-224 (ADR-99)** by migration `20261231100000_drop_model_block.sql`, with `coach_block_model_input(date)`, `save_folder_review(...)` and `coach_folder_for_review(uuid)`; the folder review is computed on the device (ADR-97) and the block is built by the deterministic builder, so nothing reads or writes them. `coach_usage` keeps its historical rows. Kept: `coach_assert_block`, `coach_block_rep_ok` (called by `save_built_coach_block` and `save_coach_block`) and `unresolved_severe_discomforts` (reserved for the injury task). The same T-216 migration set corrected catalogue facts in `exercises` (secondary muscles, primary group, movement pattern, `counts_as_strength`) from `scripts/catalogue-review-corrections.md` (`07` §3 "Catalogue facts the review reads").
- `routine_folders` (`delete_routine_folder(p_id)` raises `23503` while the folder holds a non-archived routine, deletes archived ones and returns their count; ADR-95, `04` §4.15); `routines` (name unique per user, folder_id, `track_as_routine`, `is_next`, pinned_note); `routine_exercises` (position, superset_group, target_rpe, rest_seconds, legacy summary columns) and `routine_exercise_sets` (planned weight/reps/type per set, ADR-54).
- `training_preferences` (one per user): warm_up_included, previous_values_mode, bar_weight_kg, plate_kg, dumbbell_handle_kg, auto_update_routine (global, ADR-70); "Mi entrenamiento" (T-149, US-65): intention (enum `training_intention`: strength, muscle, fat_loss, recomposition, maintenance; nullable), place (enum `training_place`: home, gym, other; nullable), equipment (`equipment[]`, default empty), days_per_week (1-7, nullable), session_minutes (15-180, multiple of 5, nullable). Saved by a direct upsert of these five columns, not by `save_preferences`.
- `workout_sets` and `routine_exercises` carry `notes text null` (T-148: check 1-200 chars, blank stored as null; set notes are never copied to routines and `update_routine_from_session` leaves routine notes untouched). The live session reads the routine's exercise notes by `routine_id` at load (no snapshot). `workout_sessions`: routine_id (set null on routine delete), name snapshot, status, started_at/ended_at, description, gym, paused_at, paused_total_s, exercise_rests. `workout_sets`: session, exercise, exercise_position, superset_group, set_index, set_type, rpe (6-10), weight_kg, reps, duration_s, distance_m, steps, floors, completed_at (null = pending).
- Rep range (T-159, US-70): `routine_exercises.rep_min/rep_max smallint null` (both null or both set, 1-50, min <= max; legacy `target_reps` untouched) and a snapshot `workout_sets.rep_min/rep_max` copied by `start_workout_session` from the routine exercise (free workouts and `save_completed_workout` leave it null). `save_routine` accepts optional `rep_min`/`rep_max` per exercise (both or neither, else `22023`); `update_routine_from_session` carries the range over.
- `coach_confirmed_values` (T-157, `04` §7, `07` §2): PK `(user_id, key)` with `key` enum `coach_value_key`; `estimate` (server estimate at confirmation: activity factor, kcal, kg per week or experience ordinal 0-2), `uncertainty` (half-width, >= 0), `level_value` (confirmed or edited activity level, only for `activity_level`), `edited`, `confirmed_at`, `updated_at`. RLS owner-only (select/insert/update, no delete); written by `confirm_derived_values`. It is not part of the coach history, so "Eliminar historial del entrenador" keeps it; deleting the account removes it (cascade).

- `coach_usage` (T-160, `07` §11): PK `(user_id, month)`, `month` the first day of the UTC month (check), `input_tokens`, `output_tokens` (bigint >= 0), `cost_eur` numeric(12,6) >= 0, `updated_at`. RLS owner select only, no insert/update/delete privilege for `authenticated`; written only by `coach_record_usage(p_user, p_month, p_input, p_output, p_cost)` (atomic upsert that adds to the row) and totalled by `coach_global_month_cost(p_month)` (one number), both `security definer`, `service_role` only. Removed with the account (cascade).

- `coach_plans` (T-161, `04` §8): `id`, `user_id`, `block_start`, `block_weeks` (1-12, default 4), `intention` (`training_intention`), `nutrition` jsonb object, `outcomes` jsonb array (default `[]`), `method` jsonb object (model, attempts, cost, constants version), `status` (`proposed|accepted|superseded|discarded`, check), `data_version` (1), `created_at`, `accepted_at`, `updated_at`. Partial unique indexes: at most one `accepted` and one `proposed` plan per user. RLS owner select only; written only by the RPCs of §6. `nutrition` (data_version 1): `intention, weight_kg, expenditure_kcal, expenditure_source, rate_pct_week, rate_kg_week, target_rate_pct, limited_by (null|floor|goal_range|deficit_cap), floor_kcal, target_kcal, calorie_adjustment, strategy, phase, phase_reason, phase_options {cut_rate_pct, diet_break}, diet_break (null or the week-4 maintenance figures), protein_pct, carbs_pct, fat_pct, protein_g, carbs_g, fat_g, protein_g_per_kg, distribution {per_meal_g, g_per_kg, min_meals}, requires_confirmation, unconfirmed[], edited_by_user, calorie_changes` and, since T-181, `activity {cardio_min_week, cardio_edited, cardio_band, steps_day, steps_basis, steps_avg}` (absent on older plans, `04` §8.8). `outcomes[]`: `{kind (weight|e1rm), key, target_value, unit, reason, deadline, basis}`. **Phase (T-187, ADR-86, `04` §8.9):** `coach_plans` also has `phase` (`coach_phase` enum: `cut|gain|maintenance|recomposition|minimal`, not null; T-200, ADR-91: `regain` removed by recreating the type, since Postgres cannot drop an enum value; a stored `regain` plan became `maintenance` with reason `intention` and the retired reason code `regain_retired` is recorded only in the migration comment, with calories, macros and block untouched), `phase_reason` (check: `intention|underweight`; `returning_break` and `returning_injury` retired by T-198 and T-200, stored rows rewritten to `intention`) and `phase_options` jsonb (default `{"cut_rate_pct":0.5,"diet_break":false}`; check: object, `cut_rate_pct` 0.5-1.0, `diet_break` boolean). The plan JSON (`nutrition.phase`, `.phase_reason`, `.phase_options`, `.diet_break {target_kcal, calorie_adjustment, strategy, protein_pct, carbs_pct, fat_pct, protein_g, carbs_g, fat_g, week: 4}`) is the source and the columns mirror it; the one exception is a minimal block, which sets the columns to `minimal` / `user_busy` and leaves `nutrition.phase` (the calories) as it is. A trigger gives a row inserted without a phase the one its intention implies (fat_loss cut, muscle gain, recomposition recomposition, maintenance and strength maintenance). Backfilled from the intention. Table grants and RLS unchanged.
- `coach_recommendations` (T-161, US-74): `id`, `user_id`, `plan_id` (nullable, cascade), `kind` (`plan|calorie_change`, text + check so later tasks swap the check), `payload` jsonb, `reason` (a code such as `rate_outside_interval`; Spanish text lives in the UI), `input_summary` (the `coach_summary` used), `status` (`pending|accepted|discarded|superseded`; T-229: `edited` removed, rows turned into `accepted`; `superseded` = replaced by a newer calorie proposal, counted nowhere), `created_at`, `decided_at` (null iff pending, check). Partial unique index: one `pending` `calorie_change` per user. RLS owner select only. Both tables are removed with the account (cascade).
- `coach_changes` (T-227, `04` §4.14): changes the coach applies on its own and flagged progressions. `id`, `user_id` (cascade), `plan_id` (nullable, cascade), `kind` (`load_raise|load_drop|load_kept|load_flag|no_range_flag|deload_triggered|deload_scheduled|deload_user`, text + check; the deload kinds were added by T-230 and carry reason `no_e1rm_improvement|seven_weeks_without_deload|user_request`, `figures` `{week, lifts?, training_weeks?}` and no exercise), `exercise_id` (nullable only for the deload kinds, check), `source_session_id` (set null; null for the raise created by deciding a flag), `origin_flag_id` (self reference, set null), `before_values` / `after_values` (jsonb arrays or null: `[{routine_id, exercise_id, rep_min, rep_max, sets:[{set_index, set_type, target_weight_kg, target_reps}]}]`, keyed by routine and exercise because ADR-70's update re-creates `routine_exercises` ids), `reason` (code: `all_sets_at_max|two_sessions_below_min|one_session_below_min_after_gap|kept_discomfort|step_over_10_percent|no_rep_range`; Spanish text in the UI), `figures` jsonb (raise/drop `{weight_from_kg, weight_to_kg, reps_best, rpe_max, sessions, step_kg}`; flag `{current_kg, step_kg, next_kg, percent, rep_min, rep_max}`; kept `{weight_kg, reps_best, rpe_max, level}`), `status` (`applied|undone|pending|decided`), `decision` (`raise|keep|range_added`), `created_at`, `decided_at` (not null iff `undone` or `decided`, check). Indexes: `(user_id, created_at desc)`, unique `(user_id, source_session_id, exercise_id)` where the session is not null (idempotence), unique `(user_id, plan_id, exercise_id)` where kind is a flag and status `pending` (no duplicate flag). RLS owner `select` only: clients have no insert, update or delete policy or privilege, because undo trusts `after_values`; every write goes through the three RPCs below, which are `security definer` with `search_path = ''` and scope each statement to `auth.uid()`. Removed with the account (cascade). RPCs (authenticated only): `apply_coach_progression(p_session_id)` -> jsonb array of `{id, kind, exercise_id, status, reason, figures, before_values, after_values, decision}` (`[]` outside an accepted block, for a stale or deload-week session, or when nothing is due; `22023` only for a null id); `undo_coach_change(p_id)` -> `{restored, skipped}` (`P0002` unknown or foreign id, `P0001` messages `coach_change_conflict` / `coach_change_not_undoable`); `decide_progression_flag(p_id, p_decision)` (`raise|keep`) -> `{flag, change}` (`22023` bad decision or a flag that is not decidable, `P0002`, `P0001` `coach_change_conflict` / `coach_change_not_pending`). A raise whose new weight is not above the highest working weight already planned in the block writes nothing and creates no row (the coach never lowers a plan). Internal invoker helpers: `progression_decision_core(p_uid, p_session_id, p_include_self)` (the body of `progression_suggestions`, which delegates with `false`), `coach_load_step`, `coach_session_in_deload`, `coach_re_snapshot`, `coach_find_re`, `coach_top_weight`, `coach_block_targets`, `coach_targets_snapshot`, `coach_refresh_summary`, `coach_write_load`, `coach_change_json`.
- `coach_plan_sessions` (T-163, `04` §9): `id`, `plan_id` (cascade), `user_id` (cascade), `week` (1-4), `deload` (boolean, default false; set by later tasks), `session_index` (1-7; unique per plan, week and index; one row per week and session, 4N rows for N sessions), `session_id` (nullable, the completed workout of that week), `name`, `focus` text[] (muscle groups), `exercises` jsonb array (`{exercise_id, exercise_key, role main|isolation, muscle_group, sets, rep_min, rep_max, rest_seconds, reason}` in order), `routine_id` (null until saved, shared by the weeks of a session_index; set null if the routine is deleted), `created_at`. - **Equipment items (T-201, ADR-92):** `equipment` gains `ez_bar` ("Barra Z", the 20 `ez-bar` catalogue rows) and `cardio_machine` ("Máquina de cardio", the eight cardio rows); the five T-184 cardio values stay in the Postgres type, unused, and `training_preferences` refuses them in new writes (`training_preferences_no_old_cardio_values`).
