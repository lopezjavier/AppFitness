# Design System - Kinetic Dark (Compose implementation)

Live summary of what is built in `composeApp/.../designsystem/`; full tables, component specs and swipe/haptics details are in [`phase1/05-design-system.md`](phase1/05-design-system.md) (frozen). §8 (rules), §9 (templates) and §10 (glossary) are the UX rulebook (ADR-69) and prevail. The Stitch mockups (style reference only) were removed after Phase 1; they exist in git history only. Section numbers are cited by code; do not renumber.

## 1. Principles
1. Dark mode only, high contrast. 2. Depth through tonal layers + micro-borders, not shadows. 3. Meaningful colour: each accent is a domain, never decorative. 4. One hand: primary actions in the lower 60 %, targets >= 48 dp. 5. Bottom sheets for contextual flows; dialogs only for destructive confirmations (R-08). 6. Immediate feedback: skeletons, haptics on set completion and goals. 7. Tabular numerals for all telemetry.

## 2. Color
### 2.1 Surfaces and text
`surfaceBase #0B0F14` (background, bars) · `surfaceRaised #121820` (cards) · `surfaceOverlay #1A222D` (sheets, inputs, chips) · `borderSubtle` white 8 % · `borderStrong` white 12 % · `divider` white 4 % · `textPrimary #E0E2EA` · `textSecondary #C2CAB0` · `ghostData` white 36 % (previous values, placeholders; never the only cue) · `scrim` black 65 %.
### 2.2 Accents
`neonLime #A3E635` (primary, success, active tab, kcal ring; `onNeonLime #0B0F14`) · `athleticCyan #38BDF8` (training: timer, 1RM, volume, filters, weight chart) · `energyAmber #F97316` (warnings, excess) · `electricGreen #22C55E` (favourable trend, synced) · `error #FFB4AB`/`onError #690005`, `errorContainer #93000A`/`onErrorContainer #FFDAD6`.
### 2.3 Macros (fixed everywhere)
Protein `macroProtein` lime `#A3E635` · Carbs `macroCarbs` cyan `#38BDF8` · Fat `macroFat` amber `#F97316`.
### 2.4 Mapping to Material 3 `darkColorScheme`
`primary = neonLime`, `secondary = athleticCyan`, `tertiary = energyAmber`, `background = surface = surfaceBase`, `surfaceContainerLow = surfaceRaised`, `surfaceContainer/High = surfaceOverlay`, `onSurface = textPrimary`, `onSurfaceVariant = textSecondary`, `outline = borderStrong`, `outlineVariant = borderSubtle`, error roles as above; every other role is set explicitly so no M3 baseline colour leaks (`ColorScheme.kt`). Non-M3 tokens (macros, ghostData, electricGreen...) are in `AppColors` via `AppTheme.colors`.
### 2.5 RPE scale (only inside `RpePickerSheet`, ADR-55)
`AppTheme.colors.rpeScale(value)`: nine stops green -> red (`#22C55E #65D04A #A3E635 #D4D93A #FACC15 #FB923C #EF4444 #E5383B #DC2626`) spread over RPE 6-10 (whole numbers, ADR-56); rows are `surfaceOverlay` tinted 16 % with an 8 dp marker bar. `confidenceScale(value)` (ADR-72) reuses the stops reversed for 1-10; it colours only a graphic >= 12 dp, text stays `textPrimary`.
**Score ramp (T-216).** `AppTheme.colors.scoreScale(score)` maps a 0-10 score onto the same nine stops reversed (0 = red `#DC2626`, 10 = green `#22C55E`, interpolated; no new colour). It tints only the `ScoreRing` arc and its band pill text (graphic >= 12 dp); the number stays `textPrimary`, and the band is always also text: Mejorable below 5,0, Aceptable 5,0 to 7,9, Buena 8,0 to 9,9, Completa 10,0. The compact `PercentRing` does not use the ramp (similarity is neutral): one `athleticCyan` arc.
### 2.6 Discomfort scale (ADR-81, T-152)
`AppTheme.colors.discomfortScale(level)`: five fixed stops taken from the RPE ramp, never the lime of "Guardar" (`#A3E635`): level 1 `#D4D93A`, 2 `#FACC15`, 3 `#FB923C`, 4 `#EF4444`, 5 `#DC2626` (all >= 3:1 on `surfaceOverlay` as a graphic). Marker bar and dot only (>= 12 dp); the label is `textPrimary` and the level is always also text (R-41).

## 3. Typography
Plus Jakarta Sans (OFL, weights 400/600/700/800); every style sets `fontFeatureSettings = "tnum, lnum"`. Styles (size/line, weight): `displayHero` 36/40 (tablet 48/52) 800 · `headlineMetric` 26/30 (32/36) 700 · `titleLarge` 20/26 600 · `titleMedium` 16/22 600 · `bodyLarge` 16/24 · `bodyMedium` 14/20 · `bodySmall` 12/16 · `labelNumeric` 18/22 700 · `labelTechnical` 11/14 600 UPPERCASE (callers pass `text.uppercase()`).

## 4. Spacing, shape and elevation
8 dp grid, 4 dp sub-grid: `none 0, xs 4, sm 8, md 12, lg 16, xl 24`. `screenMargin` 16, `cardGap` 12, `blockGap` 24, `cardPadding` 16. Radii: `sm 4`, `base 8` (inputs, rows), `md 12`, `lg 16` (cards), `xl 24` (sheet top), `full`. Elevation through layers; shadows only on sheets and the active-element lime glow (`AppElevation`).

## 5. Adaptive layout
Compact (< 600 dp): bottom navigation with 4 tabs (Diario, Entreno, Trainer, Perfil; ADR-37, ADR-79), single column. Medium/Expanded (>= 600 dp): `NavigationRail`, two asymmetric columns; forms and root screens are centred at `FormContentMaxWidth` (480 dp). Active tab: lime icon + extra-bold lime label, filled glyph where one exists, no pill (ADR-22).

## 7. Accessibility
AA contrast (4.5:1) on `surfaceBase`/`surfaceRaised` (except supporting `ghostData`); targets >= 48 dp; `contentDescription` on actionable icons; bars/rings expose `stateDescription`; font scaling to 130 % without clipping key numbers; auto-sized labels >= 11 sp. ## 8. Interaction rules and UX rulebook (ADR-45, amended by ADR-69)
Generic rules cited by number; ux-reviewer rejects plans and diffs that break one. A convention stated by the user at a checkpoint is written here.
### Navigation
- **R-01 Titles.** Tab roots show their own compact header, never a bar repeating the tab label. A screen about one object is titled with its name; an editor with verb + object ("Nueva rutina", "Editar rutina").
- **R-02 Object actions** go in the top bar: at most 2 icons plus a ⋮ action sheet; never an extra icon row under the bar, never inside one tab/section.
- **R-03** A navigation entry is a `NavigationRow` (label, optional value, chevron). The history or calendar of X is a calendar icon in X's top bar.
- **R-04** An entry's label equals the title of the screen it opens. A sheet opened from a row is titled with that row's label ("Nivel de actividad"), and a tab root's header equals its tab label ("Trainer"). Every tab root carries the notification bell in all its states (loading, error, offline; guard G13).
- **R-05** Bottom navigation appears only on tab roots; every other screen has a back arrow.
- **R-55 One row, one editor; nothing opens on its own (Checkpoint E13-D feedback, user, 2026-11-02).** Each value row of a summary (for example "Antes de empezar", "Tus datos") opens its own focused editor that shows only that value: a picker (R-12) for a choice, an Edit sheet for one number or a stepper, a full-screen editor only for long text. Two rows never open the same multi-field screen, and the same value opens the same editor from every place it is shown. No editor, questionnaire or intake opens by itself before or after an action: it opens only when the user taps its row.
### Templates
- **R-06** Every screen is built on `AppScreen` (read) or `AppEditorScreen` (edit); none draws its own top bar, footer, message host or offline banner.
- **R-07** Every bottom sheet is one of four archetypes: Edit (form + pinned footer), Picker (one choice applied on tap, no footer), Actions (menu), Info (help/read-only). A plain single-choice Picker list uses `OptionPickerSheet` (`designsystem/`, R-39). Each has a header (title, optional "?", close X "Cerrar"), scrolling body, optional pinned footer.
- **R-08 Dialogs** only to: delete the account; sign out; discard an in-progress workout; remove a training block (keeps its routines); discard unsaved changes (R-14). Nothing else.
- **R-09** The primary action of a sheet or editor is pinned and always visible.
### Editing
- **R-10** Every edit surface has an explicit "Guardar"; closing (X, back) never applies anything.
- **R-11** In an editor every change, removals included, waits for "Guardar". Immediate deletion exists only outside editors (list or details).
- **R-12** "Guardar" writes to the server. "Listo" applies to the unsaved changes of the screen underneath, which has its own "Guardar". Single-choice pickers apply on tap, no "Listo". Card lists count as single-choice: a sheet whose only control is one choice from a list uses `AppPickerSheet`, never `AppEditSheet` with a footer (guard G14 allow-lists the multi-field `AppEditSheet` users).
- **R-13** After a successful "Guardar" the editor closes and returns, with a Confirm haptic; a message only if the change is not visible there.
- **R-42 Live settings.** A switch on a read screen (`AppScreen`, no other fields, no "Guardar") applies on toggle: optimistic update, Reject haptic + message and rollback on failure, disabled offline with the standard hint (R-30). Its effect must be visible on the same screen. A switch inside an editor (Preferencias) is a draft until "Guardar" (R-10/R-11). The plan proposal's cut rate and diet break (T-188) use it, with an in-row progress indicator while saving; the reminder switches live in Preferencias → "Avisos" (T-138). Plan-generation options on a proposal are not settings, so R-10/R-11 do not apply to them.
- **R-45 Scales explain themselves.** A numeric or ordinal scale (for example the 1-5 "Energía" of the weekly check-in, the discomfort level, RPE, the photo "Confianza") shows a `HelpButton` (R-32) next to its label that opens an Info sheet listing what each value means (one bullet per value; a 1-10 scale may group values in bands). Exempt: options that already carry their own description in place (activity-level cards), categorical choices (strategy, set type, goal, units) and continuous quantities (macro sliders, durations). A coloured scale of long labels is a list of `ScaleOptionRow`s (RPE, discomfort level), not chips (R-33 exception). Added at Checkpoint E12-A (user feedback, 2026-10-29); T-152 sweeps every existing scale.
- **R-46 Non-obvious options explain themselves (Checkpoint E12-B feedback, 2026-10-29).** Any option, choice or free-text field whose meaning is not obvious at a glance (for example "Ganar fuerza" vs "Ganar musculatura", the set-note field: what to write there and why) shows a `HelpButton` (R-32) opening an Info sheet with one line per option or, for free text, what it is for and one or two real examples. R-45 is the case of scales. ux-reviewer lists every such option in the plan; when in doubt, add the `?`.
- **R-47 Few-value numeric choices are not dropdowns.** Durations, counts and other bounded numbers (session length, days per week) use the same control as "Descanso" and "Objetivo RPE" of the routine editor, never a dropdown menu. Durations drop zero parts: "1 min", "1 h", "1 h 30 min" (never "1 h 0 min"), in every screen and in the shared formatter.
- **R-48 Add-actions of a long picker are pinned.** In a scrollable selection list (exercise picker), the "Añadir ejercicio propio" action is fixed at the bottom of the sheet and never scrolls with the list.
- **R-50 Table columns line up.** In any table-like list (live session sets, workout editor), each header label is centred over the field below it and every row uses the same column widths as the header. A column that repeats what the row already says is dropped: the live set table has no "Nº" column and no per-set numbers; only "Tipo" (set type) stays, plus KG, REPS, RPE and LISTO (user, 2026-10-29).
- **R-49 Per-row actions are integrated.** A secondary per-row action (set note) uses the row's own layout (an icon inside the row or its trailing slot), not a free-floating icon on a line of its own below it.
- **R-51 Exercise status rows (live session, Checkpoint E13-A feedback, 2026-10-29).** Per-exercise information in the live session card follows one structure, top to bottom: heading (name, ⋮) with its static target ("Objetivo RPE 9") as a secondary line right under the name, never a row of its own; then up to three `ExerciseStatusRow`s in fixed order (molestia, nota, sugerencia); then the set table; then "Añadir serie". All status rows share one grammar: `surfaceOverlay` rounded box, >= 48 dp, a leading marker (coloured dot for discomfort, info icon otherwise), one line of `bodyMedium` text, and at most one trailing action that lives inside the row (a text action or a chevron); a status row is never followed by a second control bar and never has its own `?`. A row that opens something is tappable as a whole (`Role.Button`, `onClickLabel`). Discomfort's "Ya no me molesta" is the trailing text action of its row; the suggestion row opens the reason Info sheet (R-32 satisfied by the sheet; no separate `?`); the note row opens the note editor. The live session never repeats a help the routine builder already gives: no `?` for "Objetivo RPE" (the RPE scale is explained by the RPE picker sheet where the value is chosen). Help stays only where a new scale is chosen (discomfort level sheet, R-45). Nothing is collapsed: each row appears only when it has data; rarely used actions stay in the exercise ⋮ menu. Retires: the discomfort block with its own bordered button, the free `?` next to the target and the suggestion, `InlineNote` as the live note row.
- **R-14b** A second way out of an editor (for example "Ahora no") is `AppEditorScreen.secondaryAction`, pinned under "Guardar"; a save error goes in `footerNotice`, above "Guardar", never at the end of the scroll. "Ahora no" is also the decline of a calorie proposal (T-229), a different component: the `CoachProposalCard` button, not an editor secondary action.
- **R-14** A full-screen editor with unsaved changes asks "¿Descartar los cambios?" [Descartar] [Seguir editando] on back/X; without changes it leaves silently. Sheets discard silently.
- **R-15** Creating/renaming a named item without its own editor (meal, folder, "Guardar como comida", "Guardar como rutina") uses the Name sheet: one autofocused field, keyboard "Hecho" saves when valid, names unique per user ignoring case and surrounding spaces.
### Lists, rows, add and delete
- **R-16** One row component per object type: `FoodEntryRow`, `ExerciseRow`, `WorkoutRow`, `MeasurementRow`, `NavigationRow`.
- **R-17** Tapping a row opens its details; editing starts there. In a picker, tapping picks; the thumbnail or ⓘ opens details.
- **R-18** Tapping a food or exercise name opens its details on every screen.
- **R-54 Exercise names come from one resolver (Checkpoint E13-D feedback, user, 2026-11-02; third repeat after T-155 and the block preview).** Every screen shows an exercise by its real name (catalogue or the user's custom exercise), resolved by the one shared exercise-name resolver (T-199); a ViewModel hands the screen a resolved name and a composable never falls back. A generic label in place of a name ("Ejercicio", "Ejercicio sin nombre", "Ejercicio desconocido") is a bug, never a fallback; if a name can truly be missing, the behaviour is a product decision for the user. Guard: `check-ux-conventions.sh` fails on a generic exercise label in `strings.xml` (allow-list only for non-name uses such as a screen title) and on a name fallback to a string resource in feature code.
- **R-19** Row actions are icon buttons on one line. Adding to a list is one labelled `AddItemButton` ("Añadir <objeto>") at the end.
- **R-20** Delete lives: record in a list -> swipe plus the same action in its sheet/details; configuration row (meals, plates) -> trash icon in the row; folder -> "Borrar carpeta" item in its ⋮ menu (no trash icon in the row; T-214); object on screen -> top bar. Never "Deshacer" for a deletion; the only "Deshacer" is the undo of an applied coach load change (ADR-88, T-228).
- **R-21** Swipe-to-delete uses the shared component: right to left only; "Eliminar" for saved records, "Quitar" inside editors; arms at 50 % of row width (visual change + Armed haptic), disarms below 40 % (Disarmed haptic); releasing armed deletes (Confirm haptic, row slides out, gap closes, item leaves at once); releasing early or an unarmed fling springs back; stable row keys.
- **R-22** Reordering uses the shared component: handle drags at once, Tick haptics on pick-up and each pass, auto-scroll near edges, TalkBack actions "Subir"/"Bajar".
- **R-23** Lists are lazy and animate insertions, removals and moves (`appAnimateItem()`, stable keys; snaps with animations disabled).
### Forms
- **R-24 Text fields:** label above in sentence case; one label style and focus treatment; optional trailing slot (clear, ✓, unit); names start with a capital; keyboard "Siguiente" between fields, "Hecho" on the last (in a one-field sheet "Hecho" saves).
- **R-25 Numeric fields** select all on focus, use the decimal keyboard, check ranges inline ("Entre X y Y <unidad>").
- **R-26 Search fields** use `AppSearchField` (search icon, clear button, keyboard "Buscar").
- **R-27 Validation** appears under the field after the first edit while "Guardar" stays disabled; messages follow the templates in §10.
- **R-53 Ask only what is used (Checkpoint E13-D feedback, user, 2026-11-02).** A question, field or option is shown only if its answer changes a figure or reaches the model in the same release; "a later task will read it" is not enough: the question ships with its first reader. The plan of every task that adds an input names its reader (file and figure or request); ux-reviewer rejects an input without one. Free text counts as used only when it is actually sent (shown in "Lo que el entrenador sabe de ti"). When a reader is removed, its question goes in the same task.
### Feedback and states
- **R-28 Messages:** one app-level message host above the bottom bar and any pinned footer; messages survive navigation and have no action buttons.
- **R-29 Haptics** only through `AppHaptics`, one vibration per action: Confirm (saved, added, deleted, set completed), Reject (refused/failed), Armed/Disarmed (gesture threshold), Tick (stepper/reorder step). Alerts such as the end of rest use the `Haptics` port alert pattern.
- **R-30 Offline:** only the shell shows "Sin conexión"; a write disabled offline shows the standard hint; a failed offline load shows `OfflineState`, which retries on reconnect.
- **R-31 States:** loading = skeleton shaped like the layout; empty = `EmptyState` with at most one action; error = `ErrorState` with "Reintentar"; an action waiting for server/AI shows progress ("Estimando…") and then its result or an error with "Reintentar". Every outcome is visible.
- **R-32** Help is always `HelpButton`, never text expanding in place.
- **R-43 Watch data.** Every screen that shows watch data (Health Connect: weight, sleep, steps, calories, resting heart rate) shows the Health Connect status line and its "Sincronizar" button (`HealthStatusLine`) directly under the top bar, in every state (loading, empty, error, content). Today: Peso and Actividad. Exception: a derived summary line inside a card (e.g. the Trainer week's "Pasos: media X de Y") does not need the status line; the source screen (Actividad) keeps it.
### Selection controls
- **R-33** Tabs (`AppTabRow`) switch sibling views of one screen; a segmented control (`SegmentedSelector`) picks one of 2-5 short options; chips filter a list or pick among many/long options. A control never changes type with the number of options.
- **R-34** The same concept uses the same control and labels. Chart ranges use `TimeRangeSelector`: "1S 1M 3M 6M 1A".
- **R-38** A picker, read-only sheet or action menu (calendar, day, metric and range pickers, info sheets, action menus) closes with its X, system back or an outside tap (ADR-80). A sheet with editable input or unsaved changes (R-11) closes only with its X, system back or "Cancelar" (ADR-71). Drag-down never closes a sheet and no sheet shows a drag handle.
- **R-39** Where an icon clearly represents an action (photo, add, remove, retry, scan) the control is an icon with a `contentDescription`; text buttons are for actions with no clear icon (ADR-71).
- **R-41** A quality/confidence level is never colour alone: a colour from the design-system scale plus text ("Confianza 7/10"), with the same text as `contentDescription`/`stateDescription` (ADR-72).
- **R-56 Favourites are marked by shape plus text (T-204).** The star toggle (`AppTopBarAction(toggled=)` in a top bar, `FavouriteToggle` in a row) is the only place a favourite changes; its `contentDescription` says the action ("Añadir a favoritos" / "Quitar de favoritos") and its `stateDescription` the state ("Favorito" / "No es favorito"). In lists a favourite shows a small filled star after the name and ", favorito" in the row description, never colour alone; favourites sort first, with no "Favoritos" sub-header.
- **R-57 Supporting detail goes behind a `?`, not inline (T-220, user 2026-11-04).** A row, card or section shows only what the user needs to read at a glance (the figure and its state). Explanations, advice ("Añade N series…"), examples ("Por ejemplo: …") and caveats go behind a `?` (`HelpButton`, Info sheet R-07/R-38; ADR-55) on that row, shown only when there is detail to show; tapping it opens the help. The `?` has a `contentDescription` naming the row ("Ayuda: Pecho") and a testTag `<screen>_<element>_help`. An inline supporting line is allowed only for one short fact of the row itself (a value, a date, a count); a line that explains, advises or gives examples is never inline. Applies to every new screen; existing inline lines were swept in T-225 and guard G18 (`check-ux-conventions.sh`, allow-list `scripts/ux-inline-text-allowlist.txt`) fails any `*_helper`/`_hint`/`_example`/`_advice`/`_tip` string not listed as a fact, disabled reason, empty state or option descriptor (R-39).
- **R-52 No generic health disclaimers (T-188).** A health line appears only when it comes from the user's own data and is tied to a decision the app takes (`07` section 7). No "consulta con tu médico", "no es un dispositivo médico" or similar app-wide; `HealthDisclaimerSweepTest` scans `strings.xml` (empty allow-list until the persistent-discomfort note, T-194).
### Wording
- **R-35** The glossary (§10) is binding: one label per concept and one concept per label.
- **R-36** Generic actions use the shared `action_*` strings (Guardar, Cancelar, Cerrar, Eliminar, Quitar, Añadir, Editar, Listo, Descartar, Aplicar, Ahora no, Seguir editando, Reintentar).
- **R-37** Messages follow fixed templates (§10): errors "No se pudo <acción>. Inténtalo de nuevo."; offline "Sin conexión: no se puede <acción>". Sentences end with a period; titles and buttons do not; use "…" not "..."; titles capitalize the first word only.
- **R-44 Dates and numbers:** dates via `AppDateFormat` (list "Hoy"/"Ayer"/"lun, 24 oct"; title "24 de octubre"; month "octubre 2026"); numbers via `AppNumberFormat`; macro grams are whole numbers outside nutrition tables.
### Process
- **R-39 Sweep.** A task that adds or changes a pattern updates every other instance (found by search) or records each in the E9 table with an owning task; a new designsystem component retires its ad-hoc copies within the same epic.
- **R-40 Guards.** `scripts/check-ux-conventions.sh` passes (CI).

No "Deshacer" for deletions (ADR-45); the only "Deshacer" undoes an applied coach load change (ADR-88) · no dialogs outside R-08 · explicit "Guardar" on every edit surface, nothing applies on close · single-choice pickers apply on tap, "Normal" resets the set type (ADR-55) · RPE whole 6-10 (ADR-56) · four tabs (Diario, Entreno, Trainer, Perfil; ADR-79) and no FAB (ADR-36) · Preferencias, statistics and "Mi entrenamiento" (goal, place, equipment, days, session length: important, so its own row in the Perfil root, not inside Preferencias; user, 2026-10-29) hang off Perfil · meal structure edited from Preferencias, never the Diario (ADR-41) · every setting (reminder switches, check-in day, ...) lives in Preferencias and is saved with its "Guardar", never in the screen it affects (checkpoint E10 feedback) · a Health Connect weight wins, today's weight is edited with the pencil (ADR-47/48) · help is explained in the app (ADR-55) · state survives leaving the app (ADR-40) · meals are deleted, never disabled, at least one remains (ADR-41) · saved meals are "comidas" (ADR-42) · no "Comparar" (ADR-48).

## 9. Patterns and templates (ADR-69)
Components that encode §8, each with a catalog entry and host tests: `ChecklistRow` (T-208; see §6), `AppTopBar` v2 (title, subtitle, back, <= 2 `AppIconButton` + ⋮ `AppActionSheet`, 56 dp on full-screen; `AppTopBarAction.badgeCount` / `AppIconButton.badgeCount` draw a count badge, no number at 0, "9+" past nine, exact count in the content description) · `AppScreen` (content width capped, optional pinned footer, wired to `AppMessages`) · `AppEditorScreen` (pinned "Guardar" with optional destructive action, discard dialog R-14, closes with haptic R-13, offline hint R-30, keyboard room) · sheet archetypes (shared header and pinned footer; keyboard "Hecho" saves when valid; top-only hairline) · Name sheet · `FoodSheet` (name, brand, ★, ✎ for manual foods; quantity/portion; live totals; collapsible details; context footer) · rows (`AppListRow` >= 48 dp with leading/headline/supporting/trailing, plus the per-object rows) · `SectionHeader`/`AddItemButton` · `MetricCard` · field upgrades (trailing slot, `imeAction`, capitalization, autofocus, select-on-focus) · `SwipeToDeleteRow` v2 · `ReorderableColumn` v2 · `TimeRangeSelector` · `AppMessages` · `AppHaptics` · `OfflineState` · `AppDateFormat` · `StepScaffold` (onboarding: fixed indicator, per-step title/helper/content, footer pinned above the keyboard, slide animation) · `AppIconButton` long-press tooltip.
### 9.0a Exercise names (R-54, T-199)
`ExerciseNameResolver` (`shared/.../domain/usecase`) is the only source of exercise names for the UI: ViewModels resolve names in the same load that builds their content (no content before names; a failed read or an id without a name is the screen's `ErrorState`/`OfflineState` with "Reintentar") and re-resolve on `observe()` after a custom exercise is created, renamed or deleted. Screens receive a non-null `String`; guard G16 in `check-ux-conventions.sh` rejects generic labels in `strings.xml` (only `exercise_detail_title`, the loading/error title, is allowed) and name fallbacks in feature code.
### 9.0 Exercise status row (R-51)
`ExerciseStatusRow(text, marker, onClick?, onClickLabel?, trailing?, supporting?, testTag)` in `designsystem/`: the single template for the discomfort, note and suggestion rows of the live exercise card (a `surfaceOverlay` box of at least 48 dp with a leading marker, one line of text and at most one trailing action inside the row; clickable rows carry `Role.Button` and a chevron; the card order is heading with the "Objetivo RPE" secondary line, then discomfort, note and suggestion rows only when they have data, then the set table and "Añadir serie"; no `?` on the live card for anything the routine builder already explains). `InlineNote` stays for read-only notices elsewhere (food, trainer); the live note row no longer uses it.
### 9.0b Phase row (T-188)
`PhaseRow(phase, reason, testTagPrefix)` in `feature/trainer`: an `AppCard` with the phase label (`titleMedium`, heading), the one-sentence reason (`bodyMedium`, `textSecondary`) and a `HelpButton` (`<prefix>_phase_help`) with the phase explanation. The proposal uses it; "Tu plan" shows the same pair as one line (`trainer_plan_phase`); the end-of-block review (T-191) reuses it. Texts come from `PhaseText`. The weekly cut rate is a `SegmentedSelector` (R-33), never chips or a sheet.
### 9.1 Swipe-to-delete
Drag shows a muted layer with icon + label; passing 50 % arms it (layer active, icon grows 1.0 -> 1.2, label bold, Armed tick); falling below 40 % disarms (lighter tick); release armed -> slide out ~200 ms then collapse ~200 ms (Confirm); release early -> spring back (damping ~0.8). Fling never deletes unless armed; right to left only; touch slop + horizontal lock so scrolling never swipes. Server failure: row reappears with "No se pudo eliminar. Inténtalo de nuevo." and Reject. TalkBack action "Eliminar <nombre>" gives the same removal.
### 9.2 Haptics
Feature code calls only `AppHaptics` meanings (`armed`, `disarmed`, `confirm`, `reject`, `tick`), implemented with `HapticFeedbackType` (Android 14: `GestureThresholdActivate`, `SegmentFrequentTick`/`SegmentTick`; Android 11: `Confirm`, `Reject`; fallbacks `LongPress`/`VirtualKey`/`KeyboardTap` for `minSdk` 26). The component that knows the outcome fires it; ViewModels only trigger `reject()`. `LocalAppHaptics` defaults to a no-op; tests provide a recording fake.
### 9.3 Swipe checklist for ux-reviewer
Uses `SwipeToDeleteRow` only (guard G7) · right-to-left, "Eliminar"/"Quitar" · arms 50 % / disarms 40 %, deletes only when released armed · haptics via `AppHaptics` · row leaves at once, failure brings it back with a message · stable keys + animation · same action in details and as TalkBack action · snaps with reduced motion, haptics stay.
