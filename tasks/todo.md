## The review rounds (US-123) *(T-281…T-284; no 👤 gate in E19, user decision 2026-11-11)*

Round 0 (T-288, the design system) goes first. Before it the PM sends the user the gallery command, the index path and the live-flow command (no gate): the user browses them himself, and anything missing or wrong in the tools becomes a `fix(T-###)` before the round starts.

Every round follows the same steps (US-123 "Reviewed in rounds", "Every change goes through the design system", "A decision becomes a rule", "Early feedback, no gates", "Behaviour does not change"):
1. **Review (the PM first runs `python scripts/gallery.py "<Area>"` and then runs ux-critic with only the path of that area's image folder, `composeApp/build/gallery/<area>/`, never `index.html` or another area's images; the PM never sends the critic a correction after launch; when needed the emulator also runs; it also proposes visual-language changes, and its proposals are tracked in `planning/ux-critic-ledger.md`; the PM appends the critic's "Research notes" to `planning/ux-research.md` in the same branch):** the area's screens and every flow, sheet and dialog reachable from them. Output: a findings list, one row per finding: screen, problem, proposed change, and the component or rule it affects (`05` §6/§8-§10, R-##). It respects "Decided - do not re-propose" (`05` §8) and proposes no behaviour change.
2. **Decision (PM ↔ user, in chat):** the PM presents the list; the user accepts, rejects or changes each item. Nothing is planned or built before that. The decisions are recorded in the round's task section (accepted, rejected, changed).
3. **Rules first (same branch, first commit):** the PM sends the decided list to ux-reviewer in rules mode, which writes it into `05` (pending until approved) and the ledger; every accepted change is written into `05` (§6 component, §8 rule, §9 pattern, §10 glossary) before code; a finding that states how something should look or work everywhere becomes an R-## rule and, when it can be checked, a guard in `check-ux-conventions.sh` (CLAUDE.md: a repeated finding becomes a check).
4. **Build the visual changes (user decision 2026-11-13, "visual first, tests last"; replaces the old fix-batch flow):** one branch per UI area, `feat/ui-<area>` (`design-system` first, then `diario`, …). **Only one area is in progress at a time:** the next area starts only after the current one was looked at in the emulator, approved by the user, had its tests fixed and was merged to `main`. The decided changes are built in batches, one commit per batch, on the area's branch. **Every batch is a new `compose-ui-developer` agent, never a resumed one, and the PM asks the user for `/clear` between batches; the next batch starts from the committed branch, `tasks/ui-test-changes-<area>.md` and the decided list, not from a previous agent's context.** No planner, no reviewers, no tests, no goldens, no ktlint/detekt and no Gradle test runs (it only checks that the app compiles). No PR and no merge per batch; "one PR per task" and "never close a task with CI red" are waived for these build commits and apply again to step 6. The sweep still covers every screen with the pattern (R-39). **Every batch commit appends to `tasks/ui-test-changes-<area>.md`** the tests and goldens that will have to change and why (known from the code just changed, e.g. "AppTopBarScreenshotTest, 3 goldens: title now W700").
5. **Look in the emulator, once, after the last batch:** the user does not install or test between batches. When all decided batches are committed, the PM tells the user to run `! python scripts/deliver-apk.py` from the area's branch and waits. Comments become more batches on the same branch (new agent each, `/clear` between), after which the user looks again. When the user says the area looks right, the build stops and step 6 (the test task) starts. **User validation is always after the last batch and immediately before the test task.**
6. **One test task per area (the last task of the branch):** the developer edits the tests and goldens from `tasks/ui-test-changes-<area>.md` and runs nothing but compile, ktlint and detekt locally; the tests and goldens run only in the PR's CI, and the developer fixes whatever CI reports; then pr-reviewer once, one PR, the PM merges it when CI is green. After the merge the PM has ux-reviewer set the ledger rows to `ADOPTED` or `REWORK` from the user's verdict (a round that changes tokens or components does not start while the previous such round has rows `IN REVIEW`), and only then does the next area start.
Common acceptance criteria for every round: the findings list was decided by the user before planning; every accepted change is in `05` first and swept everywhere it applies; no change alters what the app does (the existing host tests stay green and are only adjusted for testTags or layout, never for behaviour); new or changed UI has host tests and gallery entries; `check-ux-conventions.sh` passes; state survives leaving the app (ADR-40).
